Étape 01 · Le problème

Services & DNS

Chaque pod reçoit une adresse IP. Mais les pods sont jetables : ils meurent, redémarrent, sont déplacés , et changent d'IP à chaque fois. Brancher une application sur l'IP d'un pod, c'est bâtir sur du sable.

Le Service résout ça : c'est une adresse stable et un nom permanent posés devant un groupe de pods. Les pods derrière peuvent tous mourir et renaître : le Service, lui, ne bouge pas et répartit le trafic vers les pods vivants.

Côté résidence
Les locataires d'un appartement changent (les pods), mais l'adresse postale et la plaque à l'interphone restent les mêmes. On écrit au « 12 rue des Lilas, appartement Web », pas à « la personne qui y habite aujourd'hui ». Le Service est cette adresse fixe ; le facteur (Kubernetes) achemine au bon occupant du moment.
Étape 02 · Trois portes

Les Trois Types de Service

Selon qui doit joindre vos pods , l'intérieur du cluster ou le monde extérieur , on choisit l'un des trois types :

01

ClusterIP

Le défaut. Une adresse interne au cluster : joignable seulement par les autres pods. L'interphone privé de la résidence.

02

NodePort

Ouvre un port sur le nœud (entre 30000-32767), accessible depuis l'extérieur. Une porte sur la rue avec un numéro.

03

LoadBalancer

Demande une IP publique à un répartiteur de charge externe. L'accueil avec standardiste , surtout en cloud.

Règle simple : communication interne > ClusterIP. Exposer pour tester > NodePort. Exposer en production cloud > LoadBalancer (ou mieux, un Ingress, module 10).

Étape 03 · L'interne

ClusterIP

Le type par défaut. On le crée en deux temps : un Deployment, puis on l'« expose ». Le Service trouve ses pods… par leurs labels (le ciment du module 5 !).

Une appli a exposer $ kubectl create deployment web --image=nginx --replicas=3 Creer un Service ClusterIP devant elle (port 80) $ kubectl expose deployment web --port=80 $ kubectl get service web # note l'IP interne (CLUSTER-IP) Les pods reellement vises par le service (ses 'endpoints') $ kubectl get endpoints web

En YAML déclaratif :

web-svc.yaml apiVersion: v1 kind: Service metadata: name: web spec: selector: app: web # cible les pods portant ce label ports: - port: 80 # port du service targetPort: 80 # port du conteneur
Étape 04 · L'annuaire

Le DNS Interne

Voici la magie : dès qu'un Service existe, Kubernetes (via CoreDNS) lui crée un nom DNS. Les pods se joignent par ce nom, jamais par IP. Le nom complet suit toujours le même schéma :

Schema du nom DNS d'un service <service>.<namespace>.svc.cluster.local Exemples joignables depuis n'importe quel pod : web # meme namespace : le nom court suffit web.atelier # depuis un autre namespace prometheus.monitoring.svc.cluster.local # nom complet

Testons-le pour de vrai depuis un pod jetable :

Resoudre le nom (doit renvoyer la ClusterIP du service) $ kubectl run test --rm -it --image=busybox:1.36 --restart=Never -- nslookup web Faire une vraie requete HTTP via le nom $ kubectl run test --rm -it --image=busybox:1.36 --restart=Never -- wget -qO- web
Côté résidence
CoreDNS est l'annuaire de la résidence, tenu à jour en permanence. Personne ne mémorise les numéros (les IP) : on demande « passez-moi l'appartement Web de l'aile Atelier » et le standard compose pour vous. Un appartement change de locataire ? L'annuaire est corrigé sans qu'on s'en aperçoive.
Étape 05 · La porte sur la rue

NodePort

Pour atteindre l'appli depuis votre navigateur (hors du cluster), le ClusterIP ne suffit pas. Le NodePort ouvre un port sur le nœud lui-même.

Exposer en NodePort $ kubectl expose deployment web --type=NodePort --port=80 $ kubectl get service web # colonne PORT(S) : 80:3xxxx/TCP Le raccourci Minikube : ouvre direct la bonne URL $ minikube service web Ou juste recuperer l'URL sans ouvrir le navigateur $ minikube service web --url
Minikube vs Kubernetes réel
Sur un vrai cluster, un NodePort est joignable sur l'IP de n'importe quel nœud + le port. Sur Minikube, le nœud est dans une VM/conteneur isolé : son IP n'est pas directement accessible, d'où la commande magique minikube service qui crée le tunnel pour vous. C'est une commodité Minikube, pas une notion Kubernetes.
Étape 06 · Le standardiste

LoadBalancer

Le type LoadBalancer demande au cloud une vraie IP publique avec répartiteur de charge. C'est le standard en production sur AWS, GCP, Azure.

$ kubectl expose deployment web --type=LoadBalancer --port=80 $ kubectl get service web Sur Minikube : la colonne EXTERNAL-IP reste 'pending'... ...jusqu'a lancer le tunnel dans un AUTRE terminal (le laisser ouvert) $ minikube tunnel Puis EXTERNAL-IP recoit une IP joignable en local
Minikube vs Kubernetes réel
Chez un fournisseur cloud, un LoadBalancer provisionne automatiquement un vrai équilibreur réseau et une IP publique : EXTERNAL-IP se remplit en quelques secondes. Minikube n'a pas de cloud derrière : minikube tunnel simule ce répartiteur localement. La notion est la même, l'infrastructure derrière diffère.
Étape 07 · QCM

Vérifiez vos Acquis

QUESTION 01
Un Service offre une adresse stable devant des pods dont les IP changent à chaque redémarrage.
L'adresse fixe

C'est sa raison d'être : une façade stable qui répartit le trafic vers les pods vivants, identifiés par leurs labels.

QUESTION 02
Un Service de type ClusterIP est accessible depuis l'extérieur du cluster.
Interne seulement

ClusterIP n'est joignable que par les autres pods. Pour l'extérieur : NodePort, LoadBalancer ou Ingress.

QUESTION 03
Un pod peut joindre un service nommé « api » dans le namespace « prod » via « api.prod ».
Schéma DNS

Forme <service>.<namespace>. Le nom court (« api ») marche dans le même namespace ; on ajoute le namespace pour franchir les ailes.

QUESTION 04
Sur Minikube, un service LoadBalancer obtient son EXTERNAL-IP automatiquement, sans rien faire de plus.
Tunnel requis

Sans cloud derrière, l'IP reste « pending ». Il faut lancer minikube tunnel dans un terminal séparé pour simuler le répartiteur.

Étape 08 · Atelier

Atelier 7 : Connecter Deux Applications

Atelier 07 · Entièrement guidé

Du DNS interne à l'exposition externe

Deux apps : un nginx « backend » joint en interne par son nom, et l'exposition de l'une vers l'extérieur. Prérequis : Minikube démarré.

1 · Déployer et exposer en ClusterIP
$ kubectl create deployment backend --image=nginx --replicas=2 $ kubectl expose deployment backend --port=80 $ kubectl get svc,endpoints backend
2 · Prouver que le DNS interne marche
Depuis un pod jetable, joindre 'backend' par son nom $ kubectl run client --rm -it --image=busybox:1.36 --restart=Never -- sh # dans le shell du pod : / # nslookup backend # renvoie la ClusterIP / # wget -qO- backend # renvoie la page nginx / # exit
3 · Exposer vers l'extérieur
Supprimer le service interne, le recreer en NodePort $ kubectl delete service backend $ kubectl expose deployment backend --type=NodePort --port=80 $ minikube service backend # ouvre la page dans le navigateur
Validation

Réussi si nslookup backend renvoie une IP, si wget backend affiche le HTML de nginx (preuve que le DNS interne fonctionne), et si minikube service backend ouvre la page depuis votre navigateur. Nettoyage : kubectl delete deployment,service backend.

Étape 09 · Conclusion

Récapitulatif du Module 7

  • Le Service : une adresse et un nom stables devant des pods éphémères, qui répartit le trafic.
  • Trois types : ClusterIP (interne), NodePort (port sur le nœud), LoadBalancer (IP publique).
  • Sélection par labels : le service trouve ses pods exactement comme le ReplicaSet.
  • DNS interne (CoreDNS) : <service>.<namespace> , on communique par nom, jamais par IP.
  • Spécificités Minikube : minikube service pour NodePort, minikube tunnel pour LoadBalancer.
Côté résidence
Nos appartements ont des adresses fixes et un annuaire. Mais une application a souvent besoin de garder ses données même si son occupant déménage. Où ranger ce qui doit survivre ? Direction la cave : les volumes.
