Annexe · Au-delà de Minikube

Le Cluster Réel

Pendant quatre jours, vous travaillez sur Minikube. C'est un vrai cluster Kubernetes, monté par kubeadm, et tout ce que vous y apprenez est transposable. Mais Minikube vous rend aussi trois services silencieux : il installe le réseau, il fournit une classe de stockage, et il simule un répartiteur de charge. En production, personne ne fait ça pour vous.

Cette annexe monte un cluster à partir de deux machines nues, avec kubeadm, exactement comme on le ferait chez un client. Vous y verrez ce que Minikube masque : un cluster qui refuse de fonctionner tant qu'on ne lui a pas installé de réseau, une demande de stockage qui reste bloquée faute de provisionneur, un vrai service exposé sur le réseau de l'entreprise , et une machine qui tombe.

Comptez 45 minutes la première fois. Chaque commande est fournie, et chaque étape explique pourquoi elle existe , c'est là que se trouve l'essentiel.

Trois réseaux, à ne jamais confondre
Un cluster manipule trois espaces d'adresses distincts, et c'est la source de confusion numéro un quand on débute. Les machines ont des adresses sur le réseau physique , ici 192.168.26.0/24, qu'il faut adapter au vôtre. Les pods vivent sur un réseau virtuel entièrement interne au cluster , ici 10.244.0.0/16. Les Services occupent un troisième espace, virtuel lui aussi , 10.96.0.0/12 par défaut, que kubeadm gère sans qu'on ait à y toucher. Une adresse de pod n'existe nulle part sur votre réseau, et une adresse de machine n'est jamais attribuée à un pod. Quand vous verrez des 192.168.26.x dans les commandes qui suivent, ce sont toujours des adresses de machines.
Et c'est exactement pour ça que la plage par défaut est un piège
Le réseau de pods par défaut de Calico est 192.168.0.0/16. Si votre réseau physique est lui aussi en 192.168.x.x , ce qui est le cas de la quasi-totalité des réseaux d'entreprise et de bureau , cette plage englobe votre propre LAN. Les deux premiers espaces ci-dessus se recouvrent, et le cluster se met à router vers son réseau interne les adresses de vos propres machines : plus de passerelle, plus de DNS, et des pannes parfaitement incompréhensibles. On force donc partout 10.244.0.0/16, qui ne croise rien. C'est le piège numéro un de ce montage, et il ne pardonne pas.
Phase 0 · Les deux machines

Préparer le Terrain

à faire sur les DEUX VM
1 · Identité et résolution de noms
# Sur le futur plan de controle : $ sudo hostnamectl set-hostname k8s-master # Sur le futur worker : $ sudo hostnamectl set-hostname k8s-worker1 # Puis sur les DEUX, remplacer par vos IP reelles : $ sudo tee -a /etc/hosts <<'EOF' 192.168.26.XXX k8s-master 192.168.26.YYY k8s-worker1 EOF # Verifier que chacune voit l'autre par son nom $ ping -c2 k8s-worker1
2 · Désactiver le swap , kubeadm refuse de démarrer sinon
$ sudo swapoff -a $ sudo sed -i '/ swap / s/^/#/' /etc/fstab $ free -h # la ligne Swap doit afficher 0
3 · Modules noyau et routage , sans ça, le réseau des pods ne fonctionne pas
$ sudo tee /etc/modules-load.d/k8s.conf <<'EOF' overlay br_netfilter EOF $ sudo modprobe overlay && sudo modprobe br_netfilter $ sudo tee /etc/sysctl.d/k8s.conf <<'EOF' net.bridge.bridge-nf-call-iptables = 1 net.bridge.bridge-nf-call-ip6tables = 1 net.ipv4.ip_forward = 1 EOF $ sudo sysctl --system # Verifier les 3 valeurs a 1 $ sysctl net.bridge.bridge-nf-call-iptables net.ipv4.ip_forward
Phase 1 · Le moteur de conteneurs

containerd

à faire sur les DEUX VM
Installation depuis le dépôt Docker
$ sudo apt-get update $ sudo apt-get install -y ca-certificates curl gnupg apt-transport-https $ sudo install -m 0755 -d /etc/apt/keyrings $ curl -fsSL https://download.docker.com/linux/ubuntu/gpg | \ sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg $ echo "deb [arch=amd64 signed-by=/etc/apt/keyrings/docker.gpg] \ https://download.docker.com/linux/ubuntu jammy stable" | \ sudo tee /etc/apt/sources.list.d/docker.list $ sudo apt-get update && sudo apt-get install -y containerd.io
Configuration , l'étape que tout le monde rate
# Generer une configuration par defaut $ sudo mkdir -p /etc/containerd $ containerd config default | sudo tee /etc/containerd/config.toml >/dev/null # Basculer sur le gestionnaire de cgroups systemd $ sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml # Verifier que la valeur est bien passee a true $ grep SystemdCgroup /etc/containerd/config.toml $ sudo systemctl restart containerd && sudo systemctl enable containerd $ sudo systemctl is-active containerd
Pourquoi SystemdCgroup est critique
Ubuntu 22.04 utilise systemd comme gestionnaire de cgroups. Si containerd utilise cgroupfs pendant que kubelet utilise systemd, vous obtenez deux gestionnaires qui se disputent les mêmes ressources. Symptôme : le cluster démarre, puis les pods redémarrent aléatoirement sous charge, sans erreur claire. C'est la panne la plus pénible de ce montage, et elle n'apparaît qu'au bout de plusieurs minutes de fonctionnement , typiquement en pleine démo.
Phase 2 · Les paquets Kubernetes

kubeadm, kubelet, kubectl

à faire sur les DEUX VM
Le dépôt a changé
L'ancien dépôt apt.kubernetes.io / packages.cloud.google.com est hors service. Tous les tutoriels qui traînent encore en ligne sont périmés et échouent avec une erreur 403. Le dépôt actuel est pkgs.k8s.io, et il est séparé par version mineure : l'URL contient le numéro de version, il n'existe pas de dépôt « toutes versions ».
Choisir la version , à figer avant de commencer
# Alignez cette valeur sur la version de vos Minikube. # Sur le poste de demo : kubectl version $ K8S_VERSION=v1.__ # ex : v1.31 , mineure uniquement, pas de patch
Installation et gel des versions
$ curl -fsSL https://pkgs.k8s.io/core:/stable:/$K8S_VERSION/deb/Release.key | \ sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg $ echo "deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] \ https://pkgs.k8s.io/core:/stable:/$K8S_VERSION/deb/ /" | \ sudo tee /etc/apt/sources.list.d/kubernetes.list $ sudo apt-get update $ sudo apt-get install -y kubelet kubeadm kubectl # GELER les versions : une mise a jour auto casserait le cluster $ sudo apt-mark hold kubelet kubeadm kubectl $ kubeadm version
Pré-télécharger les images , gain de temps
Sur le master, avant l'init : sudo kubeadm config images pull. Les images du plan de contrôle arrivent pendant que vous faites autre chose, et l'init ne prend plus que quelques secondes , appréciable si vous le montrez en direct.
Phase 3 · Naissance du cluster

kubeadm init

uniquement sur k8s-master
La commande , remplacez l'IP par celle du master
$ sudo kubeadm init \ --pod-network-cidr=10.244.0.0/16 \ --apiserver-advertise-address=192.168.26.XXX \ --node-name=k8s-master
Les deux adresses de cette commande n'ont rien à voir
--pod-network-cidr=10.244.0.0/16 déclare le réseau virtuel dans lequel les pods recevront leurs adresses. Il n'existe que dans le cluster. --apiserver-advertise-address est au contraire l'adresse physique de cette machine sur votre LAN , celle que les autres nœuds contacteront pour joindre l'API server. Les voir côte à côte dans la même commande est déroutant la première fois ; elles répondent à deux questions opposées.
Copiez la sortie MAINTENANT
Les dernières lignes contiennent la commande kubeadm join avec son token. Gardez-la dans un fichier : le token expire au bout de 24 h. Si vous la perdez, on la régénère (voir Phase 5).
Configurer kubectl pour votre utilisateur
$ mkdir -p $HOME/.kube $ sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config $ sudo chown $(id -u):$(id -g) $HOME/.kube/config # Le noeud apparait, mais en NotReady : c'est NORMAL, il manque le reseau $ kubectl get nodes # CoreDNS est en Pending pour la meme raison $ kubectl get pods -n kube-system
Arrêtez-vous une minute sur cet état
Le cluster vient de naître et il est NotReady. Ses CoreDNS sont bloqués en Pending. Ce n'est pas une panne : c'est la preuve que Kubernetes ne fournit pas de réseau. Il définit une interface, le CNI, et laisse à chacun le soin de brancher l'implémentation de son choix , Calico, Cilium, Flannel, ou celle de son fournisseur cloud. Tant que rien n'est branché, aucun pod ne peut obtenir d'adresse, donc aucun pod ne peut démarrer, donc le nœud se déclare inapte. Sur Minikube, cette étape est faite pour vous avant même que la main ne vous soit rendue : vous n'avez jamais vu un cluster dans cet état.
Phase 4 · Le réseau

Calico

uniquement sur k8s-master
1 · L'opérateur Tigera
# Verifiez la version courante sur docs.tigera.io avant de lancer $ kubectl create -f https://raw.githubusercontent.com/projectcalico/calico/v3.28.2/manifests/tigera-operator.yaml $ kubectl get pods -n tigera-operator
2 · La configuration , avec NOTRE plage, pas celle par défaut
$ cat <<'EOF' | kubectl create -f - apiVersion: operator.tigera.io/v1 kind: Installation metadata: name: default spec: calicoNetwork: ipPools: - blockSize: 26 cidr: 10.244.0.0/16 encapsulation: VXLANCrossSubnet natOutgoing: Enabled nodeSelector: all() --- apiVersion: operator.tigera.io/v1 kind: APIServer metadata: name: default spec: {} EOF
3 · Attendre et vérifier , 2 à 3 minutes
$ kubectl get pods -n calico-system -w # Quand tout est Running : le noeud passe Ready $ kubectl get nodes # Confirmer que la plage appliquee est la bonne $ kubectl get ippools -o jsonpath='{.items[*].spec.cidr}' ; echo
Contrôle obligatoire
La dernière commande doit afficher 10.244.0.0/16. Si elle affiche 192.168.0.0/16, arrêtez tout : le cluster va entrer en conflit avec votre réseau physique. Supprimez l'Installation, recréez-la avec le bon CIDR, et redémarrez les pods de calico-system.
Phase 5 · Le second immeuble

Rattacher le Worker

sur k8s-worker1
La commande récupérée à la Phase 3
$ sudo kubeadm join 192.168.26.XXX:6443 \ --token <token> \ --discovery-token-ca-cert-hash sha256:<hash>
Token perdu ou expiré , depuis le master
# Regenere la commande complete, prete a coller $ kubeadm token create --print-join-command
Vérification , depuis le master
$ kubectl get nodes -o wide # Les deux noeuds Ready. Le worker n'a PAS de role : c'est normal. # Optionnel, purement cosmetique mais joli en demo : $ kubectl label node k8s-worker1 node-role.kubernetes.io/worker=
Ce que contient réellement cette commande
Elle tient en trois éléments. L'adresse du plan de contrôle et son port 6443, pour savoir à qui parler. Le token, qui prouve au cluster que cette machine a le droit de le rejoindre , il expire au bout de 24 heures, par sécurité. Et le hash du certificat d'autorité, qui joue le rôle inverse : c'est le nœud qui vérifie qu'il parle bien au vrai plan de contrôle et non à un imposteur qui aurait pris son adresse. L'authentification va dans les deux sens, et c'est volontaire.
Phase 6 · Les extras

Ce que Minikube Offrait Gratuitement

uniquement sur k8s-master

Un cluster kubeadm nu n'a ni contrôleur d'entrée, ni LoadBalancer, ni classe de stockage. Minikube fournit les trois via ses addons. C'est précisément ce qui rend ce cluster intéressant en démo , mais il faut les installer.

1 · MetalLB , un vrai LoadBalancer sur votre LAN

Attention au troisième espace d'adresses : la plage ci-dessous est sur le réseau physique, pas sur celui des pods. MetalLB distribue de vraies adresses de votre LAN, joignables depuis n'importe quelle machine du réseau. Elles doivent donc être libres et hors de la plage distribuée par votre DHCP.

$ kubectl apply -f https://raw.githubusercontent.com/metallb/metallb/v0.14.8/config/manifests/metallb-native.yaml $ kubectl wait --for=condition=ready pod -l app=metallb -n metallb-system --timeout=180s # La plage d'IP : DOIT etre libre et HORS de votre plage DHCP $ cat <<'EOF' | kubectl apply -f - apiVersion: metallb.io/v1beta1 kind: IPAddressPool metadata: {name: lan-pool, namespace: metallb-system} spec: addresses: [192.168.26.200-192.168.26.210] --- apiVersion: metallb.io/v1beta1 kind: L2Advertisement metadata: {name: lan-adv, namespace: metallb-system} spec: ipAddressPools: [lan-pool] EOF
2 · Le contrôleur d'entrée
$ kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.11.3/deploy/static/provider/baremetal/deploy.yaml # Le basculer en LoadBalancer pour qu'il prenne une IP MetalLB $ kubectl patch svc ingress-nginx-controller -n ingress-nginx \ -p '{"spec":{"type":"LoadBalancer"}}' $ kubectl get svc -n ingress-nginx # EXTERNAL-IP doit se remplir
3 · Le stockage , observez d'abord ce qui se passe sans lui
$ kubectl apply -f https://raw.githubusercontent.com/rancher/local-path-provisioner/v0.0.30/deploy/local-path-storage.yaml $ kubectl patch storageclass local-path \ -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'
Vérifiez les numéros de version
Les trois URL ci-dessus contiennent des versions figées. Vérifiez sur les dépôts GitHub respectifs qu'elles sont toujours d'actualité au moment du montage , une version trop ancienne peut être incompatible avec la version de Kubernetes que vous avez choisie en Phase 2.
Phase 7 · Contrôle

La Recette de Montage

Les huit vérifications à passer avant de déclarer le cluster prêt. Toutes doivent répondre correctement, sinon la démo cassera au pire moment.

1 - Deux noeuds, tous les deux Ready $ kubectl get nodes -o wide 2 - Aucun pod en echec, tous namespaces confondus $ kubectl get pods -A | grep -vE "Running|Completed" 3 - La plage de pods est la bonne (10.244.x.x attendu) $ kubectl get pods -A -o wide | grep calico-node 4 - Le DNS interne repond $ kubectl run dnstest --rm -it --image=busybox:1.36 --restart=Never -- nslookup kubernetes.default 5 - Un pod peut joindre l'exterieur (NAT sortant OK) $ kubectl run nettest --rm -it --image=busybox:1.36 --restart=Never -- ping -c2 1.1.1.1 6 - Le LoadBalancer distribue bien une IP $ kubectl get svc -n ingress-nginx ingress-nginx-controller 7 - Le pod se place-t-il bien sur le worker ? $ kubectl run place --image=nginx:1.25 && kubectl get pod place -o wide 8 - etcd repond (utile pour la demo du jour 4) $ kubectl get pods -n kube-system | grep etcd
Le réflexe à prendre
Si vous avez la main sur l'hyperviseur, prenez un instantané des deux machines maintenant. Sinon, sachez que la procédure de remise à zéro complète tient en quatre commandes (dernière slide) et ramène à un état sain en trois minutes. La suite de cette annexe consiste en partie à casser des choses volontairement pour observer comment le cluster réagit , mieux vaut savoir comment revenir en arrière avant de commencer.
Observation 01 · Ce qui vient de se passer

Un Nœud, ça se Déclare

Relire le rattachement

Tout un cluster tient dans cette poignée de main

Reprenez la Phase 5 et regardez-la avec du recul. Une machine nue a rejoint un cluster en une seule commande. Il n'y a pas eu d'inscription dans un annuaire, pas de fichier de configuration central à modifier, pas de redémarrage du plan de contrôle.

Un cluster, ce n'est rien d'autre qu'un plan de contrôle, et des machines qui viennent s'y déclarer. Le token dit « j'ai le droit d'entrer ». Le hash du certificat dit « et moi, je vérifie que tu es bien le bon bureau de gestion ». Tout le reste est de la conséquence.

Ce que le nœud a fait, dans l'ordre :

  1. Il a contacté l'API server à l'adresse indiquée et présenté son token.
  2. Il a vérifié le certificat du plan de contrôle contre le hash fourni , sans quoi il aurait refusé de continuer.
  3. Il a reçu un certificat client personnel, qui remplace le token dès l'instant où il est en place.
  4. Son kubelet a démarré, s'est enregistré, et a commencé à recevoir des instructions.
Le détail à ne pas rater
$ kubectl get pods -n calico-system -o wide

Un pod calico-node est apparu tout seul sur le nouveau nœud. Personne ne l'a demandé, aucune commande ne l'a créé. C'est un DaemonSet : il déclare « un pod par nœud, pour toujours », et le cluster se charge de tenir cette promesse , y compris pour les nœuds qui n'existaient pas encore au moment où la règle a été écrite.

Rejouer le rattachement autant de fois qu'on veut
--- Sur le master : sortir le worker du cluster --- $ kubectl drain k8s-worker1 --ignore-daemonsets --delete-emptydir-data $ kubectl delete node k8s-worker1 $ kubectl get nodes # il n'en reste qu'un --- Sur le worker : effacer toute trace de l'ancien rattachement --- $ sudo kubeadm reset -f $ sudo rm -rf /etc/cni/net.d --- Sur le master : regenerer une commande de rattachement valide --- $ kubeadm token create --print-join-command --- Sur le worker : coller la commande obtenue --- $ sudo kubeadm join ... --- Sur le master : suivre le retour du noeud en direct --- $ kubectl get nodes -w # NotReady puis Ready en ~30 s
Ce que révèle le drain préalable
On ne supprime jamais un nœud sans l'avoir vidé d'abord. drain déplace ses pods ailleurs et le marque comme non planifiable ; delete node ne fait que le retirer de l'inventaire. Sans le reset côté worker, la machine garderait ses certificats et sa configuration, et refuserait de rejoindre quoi que ce soit : elle se croit encore membre d'un cluster.
Observation 02 · La comparaison

Trois Choses que Minikube Fait pour Vous

01 · Un DaemonSet qui a vraiment plusieurs pods

La couverture, pas le nombre

$ kubectl get pods -n kube-system -o wide | grep kube-proxy

Deux pods, deux nœuds, un par machine physique. Sur un Minikube mono-nœud, ce même DaemonSet n'en a qu'un, et la différence avec un Deployment à un réplica reste abstraite.

Le détecteur de fumée, ce n'est pas « un détecteur quelque part dans la résidence ». C'est un détecteur dans chaque immeuble, automatiquement, y compris dans celui qui sera construit demain. Un Deployment à deux réplicas ne garantit rien de tel : rien n'empêcherait le scheduler de placer les deux au même endroit.
02 · Une demande de stockage sans réponse

À exécuter avant d'installer le provisionneur

$ kubectl apply -f - <<'EOF' apiVersion: v1 kind: PersistentVolumeClaim metadata: {name: test-cave} spec: accessModes: [ReadWriteOnce] resources: {requests: {storage: 1Gi}} EOF $ kubectl get pvc test-cave # Pending, indefiniment $ kubectl describe pvc test-cave # "no persistent volumes available" $ kubectl get storageclass # vide !
Sur Minikube, ce PVC passerait en Bound en deux secondes. Ici, il ne se passera jamais rien. La différence tient à une seule ligne : Minikube installe un provisionneur automatique et le déclare classe par défaut. En production, soit le fournisseur cloud en fournit un, soit un administrateur crée les volumes à la main , et c'est exactement ce qu'on demande à l'examen CKA.
La réponse , installer un provisionneur automatique
Rancher local-path-provisioner : il taille les volumes dans le disque du noeud $ kubectl apply -f https://raw.githubusercontent.com/rancher/local-path-provisioner/v0.0.30/deploy/local-path-storage.yaml Attendre qu'il soit pret $ kubectl get pods -n local-path-storage -w Une classe de stockage existe enfin, mais elle n'est pas "par defaut" $ kubectl get storageclass La declarer par defaut : c'est CA qui debloque le PVC $ kubectl patch storageclass local-path \ -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}' Verifier : la mention (default) doit apparaitre $ kubectl get storageclass
Et maintenant, sans avoir touché au PVC
$ kubectl get pvc test-cave STATUS passe de Pending a Bound, tout seul, en quelques secondes $ kubectl get pv Un volume vient d'etre cree a la demande, il n'existait pas avant $ kubectl describe pvc test-cave | tail -12

Le PVC n'a pas bougé d'une ligne. Ce qui a changé, c'est que le cluster dispose enfin de quelqu'un capable de répondre à la demande. Un PVC ne crée pas de stockage : il réclame du stockage, et attend indéfiniment que quelqu'un se manifeste.

Pour rejouer la démonstration depuis zéro
$ kubectl delete pvc test-cave $ kubectl delete -f https://raw.githubusercontent.com/rancher/local-path-provisioner/v0.0.30/deploy/local-path-storage.yaml
03 · Un vrai LoadBalancer

Une adresse sur le réseau de l'entreprise

$ kubectl create deploy demo-lb --image=nginx:1.25 $ kubectl expose deploy demo-lb --type=LoadBalancer --port=80 $ kubectl get svc demo-lb # EXTERNAL-IP se remplit

Ouvrez cette adresse depuis n'importe quelle machine du réseau : le site répond. Sur Minikube, cette colonne reste sur <pending> indéfiniment, et il faut lancer minikube tunnel pour contourner.

Un Service de type LoadBalancer ne fait rien par lui-même : il demande à l'infrastructure de lui attribuer une adresse. Sur un cloud, c'est le fournisseur qui répond. Ici, c'est MetalLB. Sur un cluster nu sans aucun des deux, la demande reste en attente pour toujours , et c'est le comportement correct, pas un bug.
Observation 03 · La panne

Quand un Nœud Tombe

Méthode A · la coupure réseau , recommandée

Le nœud est vivant, mais le cluster ne l'entend plus

Plutôt que de couper le courant, on coupe la seule chose qui compte : le lien entre le kubelet du worker et l'API server. La machine continue de tourner, les conteneurs continuent de servir , et le cluster, lui, la déclare morte. C'est exactement ce qui se produit lors d'une vraie coupure réseau, et c'est bien plus fréquent en production qu'une machine qui s'éteint.

Préparation , depuis le master
$ kubectl create deploy survie --image=nginx:1.25 --replicas=4 $ kubectl get pods -o wide -l app=survie # repartis sur les 2 noeuds Ouvrir deux terminaux cote a cote et les laisser tourner : $ kubectl get nodes -w $ kubectl get pods -o wide -w
Déclencher la panne , en SSH sur le worker
Bloquer UNIQUEMENT le port de l'API server $ sudo iptables -I OUTPUT -p tcp --dport 6443 -j DROP Votre session SSH (port 22) n'est pas affectee : vous gardez la main Et on verifie que le kubelet, lui, tourne toujours : $ systemctl is-active kubelet # active
Rétablir , toujours sur le worker
$ sudo iptables -D OUTPUT -p tcp --dport 6443 -j DROP
Méthode B · encore plus simple
Si l'on veut aller au plus court : sudo systemctl stop kubelet sur le worker, puis sudo systemctl start kubelet pour réparer. Le résultat observable est presque identique. La différence : avec la coupure réseau, le kubelet est vivant et aveugle, ce qui est le cas de figure réel ; avec l'arrêt du kubelet, il est simplement absent. La méthode A raconte une meilleure histoire, la méthode B se tape en dix caractères.
Observation 03 · La chronologie

Ce que Vous Allez Voir

Chronométrez à voix haute

Trois phases, et une surprise à la fin

MomentCe qui s'affiche
T+0 à 45 sRien. Absolument rien ne bouge. Le cluster ne sait pas encore. Ce silence est la partie la plus intéressante de l'expérience.
≈ T+45 sLe nœud bascule en NotReady. Ses pods restent pourtant affichés Running : l'API server n'a plus de nouvelles, et il refuse de présumer quoi que ce soit.
≈ T+5 minLes pods du nœud injoignable passent en Terminating, et des remplaçants apparaissent sur le nœud survivant.
Au rétablissementLe nœud repasse Ready en quelques secondes, sans aucune commande. Et les pods restés en Terminating disparaissent enfin pour de bon.
Quarante-cinq secondes de silence, puis cinq minutes avant de réagir. Ce n'est pas de la lenteur, c'est de la prudence. Un nœud qui ne répond plus pendant trente secondes, c'est le plus souvent le réseau qui a hoqueté. Déplacer tous ses pods pour ça coûterait bien plus cher que d'attendre , alors Kubernetes attend d'être sûr.
La surprise , à vérifier pendant la panne, depuis le worker
Le cluster affiche ces pods en Terminating... mais sur la machine : $ sudo crictl ps | grep nginx Ils tournent toujours. Ils servent toujours du trafic.

Pendant ces minutes-là, les mêmes pods existent en double : les originaux, bien vivants sur un nœud que plus personne ne contrôle, et leurs remplaçants sur le nœud survivant. Personne ne peut ordonner aux premiers de s'arrêter, puisque justement on ne les joint plus. C'est le kubelet qui fera le ménage à son retour, en constatant que ces pods ne lui sont plus assignés.

Voilà pourquoi une base de données ne se déploie pas comme un serveur web. Deux nginx qui servent la même page en double, ce n'est pas grave. Deux bases qui écrivent en parallèle dans le même stockage, c'est une corruption de données. C'est tout le sujet des StatefulSets et du verrouillage , et la raison pour laquelle Kubernetes préfère laisser un pod en Terminating une éternité plutôt que d'en démarrer un second trop vite.

Les deux durées sont réglables , node-monitor-grace-period côté controller-manager pour la première, les tolérances automatiques node.kubernetes.io/unreachable pour la seconde. Les baisser rend le cluster plus réactif, et plus nerveux. C'est un arbitrage, pas un réglage optimal.

Et la question suivante s'impose d'elle-même : ici, c'est un worker qui est tombé, et le plan de contrôle a géré. Que se passerait-il si c'était le plan de contrôle lui-même ? C'est tout le sujet de la haute disponibilité, au module 14.

Les Sept Points de Vigilance

Si vous refaites ce montage un jour, chez un client ou pour vous entraîner, ce sont les sept endroits où l'on se plante. Aucun n'est difficile ; tous sont silencieux.

  • Le swap. kubeadm refuse catégoriquement de démarrer tant qu'il est actif. Désactivez-le dans /etc/fstab, pas seulement pour la session en cours, sinon il revient au prochain redémarrage.
  • SystemdCgroup. containerd et kubelet doivent utiliser le même gestionnaire de cgroups. Sinon le cluster démarre normalement, puis les pods redémarrent aléatoirement sous charge, sans message d'erreur exploitable.
  • Le CIDR des pods. Jamais une plage qui recouvre le réseau physique. Vérifiez toujours après installation : kubectl get ippools -o jsonpath='{.items[*].spec.cidr}'.
  • Le dépôt de paquets. apt.kubernetes.io est hors service. Les tutoriels qui l'utilisent encore échouent en 403. Le dépôt actuel est pkgs.k8s.io, séparé par version mineure.
  • Le gel des versions. apt-mark hold sur les trois paquets. Une mise à jour automatique d'un composant seul désynchronise le cluster.
  • La plage MetalLB. Elle doit être libre et hors de la plage distribuée par le DHCP, sinon deux machines finiront par se disputer la même adresse. Pinguez chaque adresse avant de la déclarer.
  • Le token de rattachement. Il expire au bout de 24 heures. Ce n'est pas une panne : on en régénère un avec kubeadm token create --print-join-command.
Ce qu'il faut retenir de cette annexe
Minikube et ce cluster font tourner exactement le même Kubernetes. Ce qui change, c'est ce qui vous est offert : le réseau, le stockage, l'exposition. Savoir ce qui est un service de votre environnement et ce qui est un service de Kubernetes est la différence entre quelqu'un qui sait utiliser un cluster et quelqu'un qui sait en administrer un.
