Étape 01 · Le plan

L'Architecture du Cluster

Une résidence Kubernetes se divise en deux zones. La zone de gestion (le « plan de contrôle », ou control plane) : c'est le bureau du syndic, là où toutes les décisions se prennent. La zone de travail (les nœuds, ou workers) : ce sont les immeubles où vivent réellement les habitants.

Chaque zone est faite de quelques composants, des petits programmes spécialisés. Comprendre qui fait quoi, c'est comprendre Kubernetes : quand quelque chose cassera, vous saurez à quel bureau frapper.

Côté résidence
D'un côté, le bureau de gestion avec ses employés (réception, cadastre, agent immobilier, contrôleur). De l'autre, les immeubles, chacun avec son gardien, son standard téléphonique et ses ascenseurs. On visite les deux.

Le Plan de Contrôle

Étape 03 · Réception & mémoire

API Server & etcd

Le kube-apiserver est le centre névralgique. C'est une porte d'entrée unique qui : reçoit toutes les demandes (les vôtres via kubectl, et celles des autres composants), vérifie que vous avez le droit et que la demande est valide, puis écrit le résultat dans etcd. Personne ne lit ou n'écrit dans etcd directement : on passe toujours par la réception.

etcd est une base de données « clé-valeur » qui stocke l'unique source de vérité : la liste de tous les objets (pods, services, configs…) et leur état désiré. Si etcd est perdu sans sauvegarde, la résidence perd sa mémoire. C'est l'élément le plus précieux du cluster.

Kubernetes réel
En production, etcd est sauvegardé religieusement et souvent répliqué sur 3 ou 5 machines pour survivre à une panne (voir module 14, haute disponibilité). Sur Minikube, il y a un seul etcd, non répliqué : si on casse le cluster, on le recrée, sans drame, puisque c'est un terrain d'entraînement.
Étape 04 · Décision & correction

Scheduler & Controllers

Le kube-scheduler ne s'occupe que d'une chose : les nouveaux pods qui n'ont pas encore d'immeuble. Pour chacun, il examine tous les nœuds disponibles, filtre ceux qui conviennent (assez de CPU/mémoire ? contraintes respectées ?), les note, et attribue le pod au meilleur. Il ne lance rien : il décide seulement où.

Le kube-controller-manager regroupe une foule de petits surveillants (les « contrôleurs »), chacun responsable d'un type d'objet. Le contrôleur de déploiement veille à ce qu'il y ait toujours le bon nombre de copies ; le contrôleur de nœud détecte les immeubles qui ne répondent plus. Tous suivent la même boucle : observer > comparer > corriger.

Côté résidence
L'agent immobilier (scheduler) dit « ce nouveau locataire ira dans l'immeuble B, il y a de la place ». Le contrôleur patrouille sans cesse : « le contrat dit 3 appartements occupés, je n'en compte que 2, j'en rouvre un immédiatement ».
Étape 05 · Les immeubles

Le Nœud (Worker)

Chaque nœud (immeuble) fait tourner trois composants qui exécutent concrètement les décisions du bureau de gestion.

01

kubelet

Le gardien de l'immeuble. Il demande à la réception « des locataires pour moi ? », puis veille à ce qu'ils soient bien installés et en vie. C'est le seul à parler à la gestion.

le gardien
02

kube-proxy

Le standard téléphonique de l'immeuble. Il programme les règles réseau pour qu'un appel vers une « adresse de service » arrive au bon appartement.

le standard
03

container runtime

Le moteur qui démarre réellement les conteneurs (containerd). C'est lui qui « emménage les meubles » dans l'appartement.

les ascenseurs / le moteur
Kubernetes réel
En production, ces trois composants tournent sur chaque immeuble du quartier, parfois des centaines. Sur Minikube, il n'y a qu'un seul immeuble qui, fait amusant, héberge à la fois le bureau de gestion et les locataires. C'est une particularité du mono-nœud : dans un vrai cluster, on les sépare.
Étape 06 · Le voyage d'une demande

Que se Passe-t-il Quand on Crée un Pod ?

Suivons une demande de bout en bout. C'est le scénario qui relie tous les composants :

  1. Vous tapez une commande : kubectl envoie votre fichier YAML à la réception (apiserver).
  2. La réception vérifie vos droits, valide la demande, et inscrit l'état désiré au cadastre (etcd). Le pod existe « sur le papier », sans immeuble.
  3. L'agent immobilier (scheduler) repère ce pod sans adresse, choisit un immeuble et note l'attribution (toujours via la réception).
  4. Le gardien (kubelet) de cet immeuble voit qu'un locataire lui est attribué et demande au moteur (runtime) de télécharger l'image et de démarrer les conteneurs.
  5. Le gardien rapporte l'état (« il est en vie ») à la réception, qui met à jour le cadastre.
  6. Le standard (kube-proxy) ajuste les règles réseau pour que le nouveau locataire soit joignable.
Côté résidence
Aucun employé ne court partout : chacun observe le cadastre et agit dans son couloir. C'est ce découplage qui rend la résidence robuste, un employé peut redémarrer sans bloquer les autres.
Étape 07 · Le réseau

La Mise en Réseau

Kubernetes impose une règle réseau simple et puissante : chaque pod reçoit sa propre adresse IP, et tous les pods peuvent se parler directement, sans traduction d'adresse, où qu'ils soient dans le cluster. Du point de vue d'un pod, tous les autres sont sur le même grand réseau plat.

Cette promesse est tenue par un plugin réseau (CNI) installé dans le cluster. Vous n'avez pas à le programmer : il câble l'immeuble pour vous. Trois niveaux d'adresses coexistent : l'IP de chaque pod (éphémère), l'IP stable d'un service (module 7), et le DNS interne qui donne des noms lisibles à tout ça.

Kubernetes réel
Le choix du plugin CNI (Calico, Cilium, Flannel…) est une vraie décision d'architecture en production, avec des conséquences sur la performance et la sécurité réseau. Minikube en installe un par défaut : on profite du réseau câblé sans s'en soucier, ce qui est parfait pour apprendre la logique avant les détails.
Étape 08 · QCM

Vérifiez vos Acquis

QUESTION 01
Toute interaction avec le cluster passe obligatoirement par le kube-apiserver.
La porte unique

Vrai. L'apiserver est le seul point d'entrée : kubectl, les contrôleurs et les kubelets lui parlent tous. Personne n'écrit dans etcd en direct.

QUESTION 02
Le kube-scheduler démarre lui-même les conteneurs sur le nœud qu'il a choisi.
Il décide seulement

Le scheduler choisit le nœud, rien de plus. C'est le kubelet de ce nœud qui, ensuite, fait démarrer les conteneurs via le runtime.

QUESTION 03
Perdre etcd sans sauvegarde, c'est perdre l'état du cluster.
La mémoire du cluster

etcd est la source de vérité unique. C'est pour cela qu'en production il est sauvegardé et répliqué avec le plus grand soin.

QUESTION 04
Dans Kubernetes, chaque pod possède sa propre adresse IP.
Réseau plat

Vrai. Le modèle réseau donne une IP par pod et permet à tous les pods de communiquer directement, grâce au plugin CNI.

Étape 10 · Conclusion

Récapitulatif du Module 2

  • Deux zones : le plan de contrôle (gestion) et les nœuds (travail).
  • Plan de contrôle : apiserver (la porte unique), etcd (la mémoire), scheduler (place les pods), controller-manager (corrige les écarts).
  • Nœud : kubelet (le gardien), kube-proxy (le réseau de service), runtime (démarre les conteneurs).
  • Le voyage d'un pod : kubectl > apiserver > etcd > scheduler > kubelet > runtime, chacun observant le cadastre.
  • Réseau : une IP par pod, communication directe entre pods, câblée par le plugin CNI.
