Étape 01 · Entrer dans le cluster

Sécurité

Toute action passe par un seul guichet : l'API server. Avant d'exécuter votre commande, il pose trois questions, dans l'ordre :

1. Authentification , « Qui es-tu ? » (montrer son identité). 2. Autorisation , « As-tu le droit de faire ça ? » (vérifier les permissions, via RBAC). 3. Admission , « Cette demande respecte-t-elle les règles ? » (validation finale).

Si l'une échoue, la requête est rejetée. Ce module couvre les deux piliers que vous gérerez le plus : l'autorisation (RBAC) et l'isolation réseau (Network Policies).

Côté résidence
L'API server est l'accueil unique de la résidence. Pour faire quoi que ce soit, on s'y présente : montrer sa carte (authentification), prouver que son badge ouvre cette porte (autorisation), et respecter le règlement intérieur (admission). Pas de badge, pas d'accès.
Étape 02 · Le système de badges

RBAC : Quatre Objets

RBAC (Role-Based Access Control) répond à « qui peut faire quoi, où ». Il combine deux idées : un ensemble de permissions (Role) et une attribution à quelqu'un (Binding).

Role

Une liste de permissions dans un namespace : « lire les pods de l'aile Atelier ». Le badge et ce qu'il ouvre.

ClusterRole

Pareil, mais à l'échelle du cluster entier (ou pour les ressources non liées à un namespace, comme les nœuds).

RoleBinding

Donne un Role à une identité (utilisateur, groupe ou compte de service) dans un namespace. Remettre le badge à quelqu'un.

ClusterRoleBinding

Attribue un ClusterRole à l'échelle du cluster. Le badge passe-partout.

Principe d'or : le moindre privilège. On donne le badge le plus restreint possible. Jamais « admin de tout » par confort.

Étape 03 · Fabriquer un badge

Créer et Tester un Role

Outil indispensable : kubectl auth can-i, qui répond « ai-je le droit ? » sans rien casser. Idéal pour vérifier ses permissions.

Mes propres droits $ kubectl auth can-i create pods $ kubectl auth can-i delete nodes Creer un Role : lecture seule des pods $ kubectl create role lecteur-pods \ --verb=get,list,watch --resource=pods L'attribuer a un compte de service nomme 'appli' $ kubectl create rolebinding appli-lecture \ --role=lecteur-pods --serviceaccount=default:appli Tester les droits d'une AUTRE identite avec --as $ kubectl auth can-i list pods --as=system:serviceaccount:default:appli # yes $ kubectl auth can-i delete pods --as=system:serviceaccount:default:appli # no
Côté résidence
On crée un badge « lecture des boîtes aux lettres de l'aile » (le Role), on le remet au robot de livraison (le RoleBinding vers le compte de service). Résultat : le robot peut regarder les boîtes, mais pas les ouvrir. Le strict nécessaire.
Étape 04 · L'identité des applis

ServiceAccounts

Les humains s'authentifient avec des certificats ou des tokens. Mais les applications aussi ont parfois besoin de parler à l'API (ex. un opérateur qui crée des pods). Leur identité, c'est le ServiceAccount.

Chaque pod tourne sous un ServiceAccount (celui par défaut s'il n'en demande pas d'autre). On lui attache un Role via RBAC pour lui donner exactement les droits dont l'appli a besoin.

Creer un compte de service $ kubectl create serviceaccount appli Lister les comptes de service du namespace $ kubectl get serviceaccounts Faire tourner un pod sous cette identite $ kubectl run mon-pod --image=nginx \ --overrides='{"spec":{"serviceAccountName":"appli"}}'
Côté résidence
Un ServiceAccount est le badge d'un robot, pas d'un humain. Le robot de ménage a son propre badge, avec ses propres droits limités. On ne lui prête jamais le passe du gardien.
Étape 05 · Cloisonner le réseau

Network Policies

Par défaut, dans un cluster, tous les pods peuvent se parler librement. Une NetworkPolicy agit comme un pare-feu : elle restreint qui peut joindre qui, par labels.

Schéma typique : tout interdire, puis n'autoriser que le strict nécessaire.

1) Tout bloquer en entree pour les pods 'app=db' apiVersion: networking.k8s.io/v1 kind: NetworkPolicy metadata: { name: db-deny } spec: podSelector: { matchLabels: { app: db } } policyTypes: [Ingress] ingress: [] # aucune source autorisee --- 2) Autoriser uniquement les pods 'role=api' a joindre la db apiVersion: networking.k8s.io/v1 kind: NetworkPolicy metadata: { name: db-allow-api } spec: podSelector: { matchLabels: { app: db } } policyTypes: [Ingress] ingress: - from: - podSelector: { matchLabels: { role: api } }
Minikube vs Kubernetes réel
Piège classique : une NetworkPolicy n'est appliquée que si le plugin réseau (CNI) sait le faire. Le CNI par défaut de Minikube ne filtre pas : la règle est acceptée mais ignorée. Pour la tester réellement, il faut démarrer avec un CNI compatible : minikube start --cni=calico. En production, le CNI choisi (Calico, Cilium…) applique ces règles pour de vrai.
Étape 06 · QCM

Vérifiez vos Acquis

QUESTION 01
Toute requête passe par l'API server, qui vérifie d'abord l'identité, puis les permissions, puis l'admission.
Trois portes

Authentification > autorisation (RBAC) > admission. Un seul guichet, trois contrôles successifs.

QUESTION 02
Un Role seul suffit à donner des droits : pas besoin de le lier à une identité.
Role + Binding

Un Role définit des permissions, mais il ne s'applique à personne tant qu'un RoleBinding ne l'attribue pas à un utilisateur ou un compte de service.

QUESTION 03
Par défaut, sans NetworkPolicy, tous les pods d'un cluster peuvent communiquer entre eux.
Ouvert par défaut

Le réseau est plat et ouvert. Les NetworkPolicies servent justement à cloisonner et n'autoriser que le nécessaire.

QUESTION 04
Une NetworkPolicy est toujours appliquée, quel que soit le plugin réseau utilisé.
Dépend du CNI

Seul un CNI compatible (Calico, Cilium…) applique les règles. Le CNI par défaut de Minikube les accepte mais ne les fait pas respecter.

Étape 07 · Atelier

Atelier 12 : Badges Limités

Atelier 12 · Entièrement guidé

Créer un compte aux droits restreints et le vérifier

On fabrique un compte de service « lecture seule » et on prouve ses limites avec auth can-i. Prérequis : Minikube démarré.

1 · Créer l'identité et son badge
$ kubectl create serviceaccount observateur $ kubectl create role voir-pods --verb=get,list,watch --resource=pods $ kubectl create rolebinding obs-binding \ --role=voir-pods --serviceaccount=default:observateur
2 · Vérifier les permissions exactes
Ce qu'il PEUT faire $ kubectl auth can-i list pods --as=system:serviceaccount:default:observateur -> yes Ce qu'il NE peut PAS faire $ kubectl auth can-i delete pods --as=system:serviceaccount:default:observateur $ kubectl auth can-i create deployments --as=system:serviceaccount:default:observateur -> no (les deux)
3 · (Bonus) Isolation réseau
Necessite : minikube demarre avec --cni=calico pour un VRAI effet Sauvegarder les NetworkPolicies de l'etape 5, puis : $ kubectl apply -f network-policies.yaml $ kubectl get networkpolicies
Validation

Réussi si auth can-i list pods répond yes pour l'observateur, et delete/create répondent no. Vous avez appliqué le moindre privilège. Nettoyage : kubectl delete sa observateur ; kubectl delete role voir-pods ; kubectl delete rolebinding obs-binding.

Étape 08 · Conclusion

Récapitulatif du Module 12

  • Trois contrôles à l'entrée : authentification, autorisation (RBAC), admission.
  • RBAC : Role/ClusterRole (les permissions) + RoleBinding/ClusterRoleBinding (l'attribution).
  • kubectl auth can-i : vérifier ses droits sans risque, y compris ceux d'une autre identité (--as).
  • ServiceAccount : l'identité d'une application, à doter du strict nécessaire.
  • NetworkPolicy : pare-feu entre pods , efficace seulement avec un CNI compatible (Calico sur Minikube).
Côté résidence
La résidence est désormais sécurisée : badges, digicodes, moindre privilège. Mais déployer chaque application à la main, fichier par fichier, devient répétitif. Et si on installait des applications entières clé en main ? Bienvenue chez Helm.
