Étape 01 · Le problème

Ingress

Pour exposer une appli, on a utilisé NodePort. Mais imaginez dix applications : dix NodePorts, dix ports bizarres à retenir (30001, 30002…), aucun nom de domaine, aucun HTTPS centralisé. Ingérable.

L'Ingress est la solution : un seul point d'entrée pour tout le cluster, qui aiguille le trafic HTTP/HTTPS vers le bon service selon le nom de domaine ou le chemin de l'URL. Un portier intelligent, plutôt que dix portes dérobées.

Côté résidence
Sans Ingress, chaque appartement aurait sa propre porte donnant sur la rue, avec un numéro à rallonge : le chaos. L'Ingress, c'est le hall d'accueil unique avec un tableau des sonnettes : le visiteur entre par une seule porte, annonce qui il vient voir, et le concierge l'oriente vers le bon appartement.
Étape 02 · Deux objets distincts

Règle vs Contrôleur

Point qui piège tout le monde : l'Ingress fonctionne grâce à deux choses séparées. L'une ne sert à rien sans l'autre.

La ressource Ingress

Le fichier de règles que vous écrivez : « monsite.local > service web ». C'est juste une intention, une liste d'aiguillages.

L'Ingress Controller

Le logiciel qui exécute ces règles : un reverse-proxy (souvent nginx) qui tourne dans le cluster et lit vos Ingress. Sans lui, vos règles sont lettre morte.

Sur Minikube, le contrôleur n'est pas actif par défaut : c'est un addon à activer (slide suivante). Sur un vrai cluster, c'est à l'admin de l'installer.

Côté résidence
La ressource Ingress est la liste des correspondances affichée au tableau (« Dupont = 3e gauche »). Le contrôleur est le concierge en chair et en os qui lit ce tableau et accompagne réellement le visiteur. Une liste sans concierge ne mène personne nulle part.
Étape 03 · Embaucher le concierge

Activer le Contrôleur

Minikube embarque un contrôleur ingress-nginx, prêt à activer en une commande :

Activer le contrôleur Ingress $ minikube addons enable ingress Verifier qu'il tourne (patienter qu'il soit Running) $ kubectl get pods -n ingress-nginx Lister les addons et leur etat $ minikube addons list | grep ingress
Minikube vs Kubernetes réel
Ici, un addon suffit. Sur un vrai cluster, on installe le contrôleur soi-même (souvent ingress-nginx ou Traefik) via Helm, et il s'adosse à un LoadBalancer cloud qui lui donne une IP publique. Le concept de règles Ingress est identique partout ; seul le déploiement du concierge change.
Étape 04 · Aiguiller par nom

Routage par Domaine

Premier aiguillage : selon le nom de domaine demandé. Soit un service web déjà déployé et exposé (en ClusterIP suffit).

ingress-host.yaml apiVersion: networking.k8s.io/v1 kind: Ingress metadata: name: site-ingress spec: rules: - host: monsite.local # le nom demande... http: paths: - path: / pathType: Prefix backend: service: name: web # ...mene a ce service port: { number: 80 } $ kubectl apply -f ingress-host.yaml $ kubectl get ingress # colonne ADDRESS = l'IP du cluster

Comme monsite.local n'est pas un vrai domaine, on l'ajoute manuellement à notre fichier hosts pour qu'il pointe vers Minikube :

Faire pointer monsite.local vers l'IP de Minikube $ echo "$(minikube ip) monsite.local" | sudo tee -a /etc/hosts Tester ! $ curl http://monsite.local
Étape 05 · Aiguiller par chemin

Routage par Chemin

Encore plus puissant : un seul domaine, mais plusieurs services selon le chemin de l'URL. Idéal pour une API et un front, ou plusieurs micro-services.

ingress-path.yaml : un domaine, deux destinations apiVersion: networking.k8s.io/v1 kind: Ingress metadata: name: multi-ingress annotations: nginx.ingress.kubernetes.io/rewrite-target: / spec: rules: - host: monsite.local http: paths: - path: /app1 # monsite.local/app1 pathType: Prefix backend: service: { name: web1, port: { number: 80 } } - path: /app2 # monsite.local/app2 pathType: Prefix backend: service: { name: web2, port: { number: 80 } } $ kubectl apply -f ingress-path.yaml
Côté résidence
Même hall d'accueil (un seul domaine), mais le concierge lit la destination précise sur le badge du visiteur : « aile 1 » ou « aile 2 ». Une seule entrée, des dizaines de chemins possibles à l'intérieur.
Étape 06 · QCM

Vérifiez vos Acquis

QUESTION 01
Une ressource Ingress sans Ingress Controller installé n'a aucun effet.
Liste + concierge

L'Ingress n'est qu'un jeu de règles. Sans contrôleur (le proxy qui les applique), rien n'est routé. Sur Minikube : minikube addons enable ingress.

QUESTION 02
Un Ingress peut router vers différents services selon le nom de domaine ou le chemin de l'URL.
Host & path

C'est tout son intérêt : un point d'entrée unique, des aiguillages par domaine et/ou par chemin vers plusieurs services.

QUESTION 03
L'Ingress remplace totalement les Services : on n'a plus besoin de Service pour les pods routés.
Ingress > Service > Pods

L'Ingress route vers des Services, qui eux atteignent les pods. Les deux travaillent ensemble, l'Ingress en façade.

QUESTION 04
Sur Minikube, un domaine fictif comme monsite.local fonctionne sans aucune configuration locale.
/etc/hosts

Le domaine n'existant pas, il faut le faire pointer vers l'IP de Minikube dans /etc/hosts pour que le navigateur le résolve.

Étape 07 · Atelier

Atelier 10 : Un Hall, Deux Ailes

Atelier 10 · Entièrement guidé

Router deux applications derrière un seul domaine

On déploie deux nginx distincts et on les expose via un Ingress par chemin. Prérequis : Minikube démarré.

1 · Activer le contrôleur
$ minikube addons enable ingress $ kubectl get pods -n ingress-nginx # attendre Running
2 · Déployer deux apps et leurs services
$ kubectl create deployment web1 --image=nginx $ kubectl create deployment web2 --image=httpd $ kubectl expose deployment web1 --port=80 $ kubectl expose deployment web2 --port=80
3 · Appliquer l'Ingress et router
Sauvegarder ingress-path.yaml (etape 5) puis : $ kubectl apply -f ingress-path.yaml $ echo "$(minikube ip) monsite.local" | sudo tee -a /etc/hosts Tester les deux chemins (nginx vs apache) $ curl http://monsite.local/app1 # page nginx $ curl http://monsite.local/app2 # 'It works!' d'apache
Validation

Réussi si /app1 renvoie la page nginx et /app2 renvoie le « It works! » d'Apache , preuve qu'un seul point d'entrée aiguille vers deux services selon le chemin. Nettoyage : kubectl delete deployment,service web1 web2 ; kubectl delete ingress multi-ingress.

Étape 08 · Pour aller plus loin

HTTPS & Production

En production, l'Ingress est l'endroit naturel pour gérer le HTTPS : on y termine le chiffrement TLS une fois, et tout le trafic interne reste simple derrière.

On ne gère plus les certificats à la main : l'outil cert-manager obtient et renouvelle automatiquement des certificats (par exemple via Let's Encrypt), et les branche sur l'Ingress.

Extrait d'un Ingress avec TLS (concept de production) spec: tls: - hosts: [monsite.com] secretName: monsite-tls # certificat gere par cert-manager rules: - host: monsite.com ...
Minikube vs Kubernetes réel
Sur Minikube on teste en HTTP avec un domaine bidon. En production : un vrai domaine pointant vers le LoadBalancer du contrôleur, cert-manager qui émet le certificat, et le HTTPS « juste marche ». L'Ingress devient la porte blindée et chiffrée de la résidence.
Étape 09 · Conclusion

Récapitulatif du Module 10

  • Ingress = point d'entrée unique HTTP/HTTPS, au lieu de multiplier les NodePorts.
  • Deux objets : la ressource Ingress (les règles) et le contrôleur (qui les exécute) , l'un sans l'autre est inutile.
  • Sur Minikube : minikube addons enable ingress + entrée dans /etc/hosts.
  • Routage par domaine et par chemin : un hall, des dizaines de destinations.
  • En prod : TLS terminé sur l'Ingress, certificats automatisés par cert-manager.
Côté résidence
Fin du jour 3 : la résidence a des adresses, des caves, des coffres et un vrai hall d'accueil. Demain, on passe administrateur : décider qui habite où, qui a le droit d'entrer, déployer des apps clé en main, et savoir réparer quand tout s'effondre.
