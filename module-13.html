Étape 01 · Le problème

Helm

Au module 9, déployer WordPress a demandé deux fichiers et plusieurs objets (Secret, PVC, Deployments, Services). Pour une application complexe, on peut atteindre vingt fichiers YAML interdépendants. Les écrire, les versionner, les mettre à jour de façon cohérente devient un métier.

Helm est le gestionnaire de paquets de Kubernetes , l'équivalent d'apt pour Ubuntu. Il empaquette toute une application (tous ses YAML) dans un chart réutilisable, paramétrable, installable en une commande.

Côté résidence
Déployer à la main, c'est monter chaque meuble pièce par pièce, avec sa propre notice. Helm, c'est l'appartement meublé clé en main : on choisit un modèle dans un catalogue, on règle deux ou trois options (la couleur des murs), et tout est livré et monté d'un coup.
Étape 02 · Le vocabulaire

Chart, Values, Release, Repo

Quatre mots à maîtriser, et tout Helm devient limpide :

Chart

Le paquet : un dossier de modèles YAML avec des trous à remplir. Le « meuble en kit » avec sa notice.

Values

Les options qui remplissent les trous : nombre de réplicas, mot de passe, type de service. Les réglages du kit.

Release

Une installation concrète d'un chart, avec un nom. On peut installer le même chart plusieurs fois sous des noms différents.

Repository

Le catalogue en ligne d'où l'on télécharge des charts (ex. dépôts publics d'éditeurs).

En une phrase : on prend un chart dans un repo, on l'installe avec des values, ce qui crée une release vivante dans le cluster.

Étape 03 · Installer l'outil

Helm sur Ubuntu

Helm est un simple binaire client (il parle à votre cluster via kubectl). Installation en une ligne :

Installer Helm via le script officiel $ curl https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash Verifier $ helm version Ajouter un catalogue (repo) et le rafraichir $ helm repo add podinfo https://stefanprodan.github.io/podinfo $ helm repo update Chercher un chart dans les repos ajoutes $ helm search repo podinfo
Bon à savoir
Helm n'installe rien sur le cluster lui-même : c'est un outil client qui lit votre configuration kubectl et applique les YAML générés. Il fonctionne donc à l'identique sur Minikube et sur n'importe quel cluster de production.
Étape 04 · Installer une application

install, list, status

On installe le chart de démonstration podinfo (une mini-application légère, parfaite pour s'entraîner) sous le nom de release demo :

Installer : cree la release 'demo' a partir du chart podinfo $ helm install demo podinfo/podinfo Lister les releases installees $ helm list Etat detaille d'une release $ helm status demo Cote Kubernetes, les objets crees par Helm sont des objets normaux $ kubectl get all -l app.kubernetes.io/name=podinfo
Côté résidence
Une release, c'est un appartement meublé effectivement installé, avec une étiquette à son nom (« demo »). On peut commander le même modèle deux fois (« demo », « demo-test ») : deux appartements identiques, gérés séparément.
Étape 05 · Régler, mettre à jour, annuler

values, upgrade, rollback

La force de Helm : changer une option et appliquer proprement, avec un historique et un retour arrière , exactement comme un Deployment, mais à l'échelle de toute l'application.

Voir les reglages disponibles du chart $ helm show values podinfo/podinfo | head -n 30 Changer une option a la volee : passer a 3 replicas $ helm upgrade demo podinfo/podinfo --set replicaCount=3 $ kubectl get pods -l app.kubernetes.io/name=podinfo # 3 pods Voir les values appliquees $ helm get values demo L'historique des versions de la release $ helm history demo Revenir a la version 1 (avant l'upgrade) $ helm rollback demo 1

Pour des réglages nombreux, on les met dans un fichier plutôt qu'en --set :

mes-values.yaml replicaCount: 2 ui: message: "Bonjour depuis Helm" $ helm upgrade demo podinfo/podinfo -f mes-values.yaml
Étape 06 · Retour au module 6

La Vraie Stack de Supervision

Souvenez-vous : au module 6, on a monté Prometheus + Grafana à la main pour comprendre. Voici la promesse tenue , la même chose en production, en une commande Helm, avec Alertmanager et des dizaines de dashboards en bonus :

Le chart officiel de supervision $ helm repo add prometheus-community https://prometheus-community.github.io/helm-charts $ helm repo update Tout installer dans le namespace monitoring $ helm install kube-prom prometheus-community/kube-prometheus-stack \ --namespace monitoring --create-namespace Acceder a Grafana (mot de passe admin par defaut : prom-operator) $ kubectl get pods -n monitoring $ minikube service kube-prom-grafana -n monitoring
Minikube vs Kubernetes réel
C'est la voie standard partout. La même commande déploie cette stack sur Minikube comme sur un cluster de 100 nœuds : Helm gère la complexité, et le chart s'adapte (découverte automatique des cibles, etc.). On comprend les rouages (module 6), puis on délègue le montage à Helm (ici).
Étape 07 · QCM

Vérifiez vos Acquis

QUESTION 01
Helm est le gestionnaire de paquets de Kubernetes : il installe une application entière (tous ses YAML) en une commande.
Le « apt » de K8s

Un chart empaquette tous les manifestes d'une appli ; helm install les déploie d'un coup, de façon cohérente.

QUESTION 02
Une « release » est la même chose qu'un « chart ».
Modèle vs instance

Le chart est le paquet (le modèle) ; la release est une installation concrète de ce chart, avec un nom, dans le cluster.

QUESTION 03
On peut revenir à une version précédente d'une release avec helm rollback.
Historique géré

Helm garde l'historique des upgrades (helm history) et permet de revenir à n'importe quelle révision.

QUESTION 04
Helm s'installe dans le cluster et fonctionne différemment selon qu'on est sur Minikube ou en production.
Outil client

Helm est un binaire côté client qui parle à l'API via kubectl. Il fonctionne à l'identique partout, sans composant à installer dans le cluster.

Étape 08 · Atelier

Atelier 13 : Le Cycle de Vie Helm

Atelier 13 · Entièrement guidé

Installer, régler, annuler, désinstaller

On manipule le cycle complet sur le chart léger podinfo. Prérequis : Minikube démarré.

1 · Installer Helm et un chart
$ curl https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash $ helm repo add podinfo https://stefanprodan.github.io/podinfo $ helm repo update $ helm install demo podinfo/podinfo $ helm list
2 · Mettre à jour puis revenir en arrière
$ helm upgrade demo podinfo/podinfo --set replicaCount=3 $ kubectl get pods -l app.kubernetes.io/name=podinfo # 3 pods $ helm history demo $ helm rollback demo 1 $ kubectl get pods -l app.kubernetes.io/name=podinfo # revenu a 1
3 · Désinstaller proprement
$ helm uninstall demo $ helm list # plus aucune release $ kubectl get all -l app.kubernetes.io/name=podinfo # tout est parti
Validation

Réussi si vous avez vu le nombre de pods passer à 3 après l'upgrade, revenir à 1 après le rollback, et tout disparaître après l'uninstall , le tout sans jamais écrire un seul YAML. C'est la puissance des paquets.

Étape 09 · Conclusion

Récapitulatif du Module 13

  • Helm = le gestionnaire de paquets de Kubernetes : une application entière en une commande.
  • Chart (le paquet), values (les options), release (l'installation), repo (le catalogue).
  • install / upgrade / rollback / uninstall : un cycle de vie complet avec historique.
  • Réglages via --set ou un fichier values.yaml.
