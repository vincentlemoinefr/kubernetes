Étape 01 · Qui décide ?

Planification Avancée

Quand vous créez un pod, comment Kubernetes choisit-il sur quelle machine le placer ? C'est le travail du scheduler (l'ordonnanceur), un composant du plan de contrôle. Par défaut, il choisit tout seul un nœud avec assez de ressources.

Mais parfois, on veut guider ce choix : « cette appli a besoin d'un disque SSD », « répartis ces copies sur des machines différentes », « réserve cette machine à un usage précis ». Ce module donne les leviers pour cela.

Côté résidence
Le scheduler est l'agent immobilier de la résidence : quand un nouveau locataire arrive, c'est lui qui décide dans quel immeuble l'installer, selon les places libres. On va lui donner des critères : étage avec ascenseur, proximité d'un ami, immeubles réservés…
Étape 02 · Choisir par étiquette

nodeSelector & Labels de Nœud

Le levier le plus simple : on étiquette les nœuds, puis on exige un nœud portant telle étiquette. Comme pour les pods, tout passe par les labels.

Voir les etiquettes des noeuds $ kubectl get nodes --show-labels Coller une etiquette sur notre noeud $ kubectl label node minikube disktype=ssd Verifier $ kubectl get nodes -L disktype

Puis, dans le pod, on exige cette étiquette :

extrait d'un pod spec: nodeSelector: disktype: ssd # ne tournera QUE sur un noeud 'disktype=ssd' containers: - name: app image: nginx
Minikube vs Kubernetes réel
Sur Minikube, il n'y a qu'un nœud : nos exercices de placement restent des démonstrations « jouet ». Sur un vrai cluster, ces étiquettes (zone géographique, type de matériel, équipe propriétaire) deviennent vitales pour répartir intelligemment des centaines de pods sur des dizaines d'immeubles différents.
Étape 03 · Préférences fines

Affinité & Anti-affinité

Plus souple que nodeSelector, l'affinité exprime des préférences, dures (obligatoires) ou douces (souhaitées) :

Node affinity : choisir le nœud selon ses labels, avec plus de nuance (« de préférence un SSD, sinon tant pis »).

Pod (anti-)affinity : se placer selon où sont les autres pods. L'anti-affinité sert à répartir : « ne mets pas deux copies de ma base sur le même nœud », pour survivre à la perte d'une machine.

Anti-affinite : eviter de cohabiter avec un pod 'app=base' spec: affinity: podAntiAffinity: requiredDuringSchedulingIgnoredDuringExecution: - labelSelector: matchLabels: { app: base } topologyKey: kubernetes.io/hostname # = par noeud
Côté résidence
L'affinité, c'est dire à l'agent : « je veux près de mon collègue » (affinité) ou « surtout pas dans le même immeuble que l'autre copie de la base » (anti-affinité). Ainsi, si un immeuble brûle, il reste toujours une copie ailleurs.
Étape 04 · Réserver un nœud

Taints & Tolerations

Mécanisme inverse des précédents. Une taint (souillure) posée sur un nœud le rend repoussant : par défaut, aucun pod ne s'y installe. Seuls les pods qui portent la toleration correspondante y sont admis.

C'est ainsi qu'on réserve des machines à des usages précis (ex. machines GPU réservées au calcul).

Souiller le noeud : plus rien ne s'y planifie sans derogation $ kubectl taint nodes minikube usage=gpu:NoSchedule Voir les taints d'un noeud $ kubectl describe node minikube | grep -i taint Retirer la taint : noter le tiret final '-' $ kubectl taint nodes minikube usage=gpu:NoSchedule-

La dérogation, dans le pod :

spec: tolerations: - key: usage operator: Equal value: gpu effect: NoSchedule # ce pod accepte la taint usage=gpu
Côté résidence
Une taint, c'est un panneau « Immeuble réservé , entrée interdite ». Personne n'y emménage… sauf ceux qui ont la dérogation officielle (la toleration). Pratique pour garder un immeuble dédié à une catégorie de locataires.
Étape 05 · Un cas réel

Pourquoi le Plan de Contrôle est Protégé

Les taints ne sont pas qu'un exercice : Kubernetes s'en sert lui-même. Dans un vrai cluster, les nœuds du plan de contrôle portent une taint qui empêche vos applications de s'y installer , pour réserver leurs ressources à la gestion du cluster.

Sur un vrai cluster, on verrait une taint comme : node-role.kubernetes.io/control-plane:NoSchedule Sur Minikube mono-noeud, l'unique noeud doit tout heberger : il n'a donc PAS cette taint (sinon rien ne tournerait). $ kubectl describe node minikube | grep -i taint # <none> par defaut
Minikube vs Kubernetes réel
C'est l'illustration parfaite de notre différence : en production, le syndic (plan de contrôle) a ses propres bureaux protégés (taint), interdits aux locataires. Sur Minikube, le syndic habite dans le seul immeuble disponible avec tout le monde , d'où l'absence de cette taint. Même mécanisme, contrainte de taille différente.
Étape 06 · QCM

Vérifiez vos Acquis

QUESTION 01
nodeSelector force un pod à ne tourner que sur les nœuds portant une étiquette donnée.
Choix par label

C'est le levier de placement le plus simple : on étiquette les nœuds, on exige l'étiquette dans le pod.

QUESTION 02
L'anti-affinité de pod sert à répartir des copies sur des nœuds différents pour la résilience.
Répartir

« Pas deux copies sur le même immeuble » : si un nœud tombe, une copie survit ailleurs.

QUESTION 03
Une taint sur un nœud attire les pods vers ce nœud en priorité.
Logique inverse

Une taint repousse les pods. Seuls ceux qui ont la toleration correspondante peuvent s'y installer.

QUESTION 04
Sur Minikube mono-nœud, l'unique nœud n'a pas la taint de plan de contrôle, sinon rien ne pourrait s'y planifier.
Tout sur un nœud

Le seul immeuble doit héberger applis ET syndic : il ne peut donc pas se repousser lui-même.

Étape 07 · Atelier

Atelier 11 : Diriger le Placement

Atelier 11 · Entièrement guidé

Étiqueter, exiger, repousser, déroger

Même sur un seul nœud, on peut observer chaque mécanisme à l'œuvre. Prérequis : Minikube démarré.

1 · nodeSelector : exiger une étiquette
$ kubectl label node minikube disktype=ssd Pod qui exige disktype=ssd $ kubectl run sur-ssd --image=nginx --overrides='{"spec":{"nodeSelector":{"disktype":"ssd"}}}' $ kubectl get pod sur-ssd -o wide # Running : l'etiquette correspond
2 · taint : rendre le nœud repoussant
$ kubectl taint nodes minikube reserve=oui:NoSchedule Un pod ordinaire ne peut plus se planifier $ kubectl run bloque --image=nginx $ kubectl get pod bloque # reste 'Pending' ! $ kubectl describe pod bloque | grep -A4 Events # 'untolerated taint'
3 · toleration : la dérogation
Un pod qui tolere la taint passe $ kubectl run avec-derog --image=nginx \ --overrides='{"spec":{"tolerations":[{"key":"reserve","operator":"Equal","value":"oui","effect":"NoSchedule"}]}}' $ kubectl get pod avec-derog # Running : la derogation marche Tout nettoyer (ne pas oublier le tiret final) $ kubectl taint nodes minikube reserve=oui:NoSchedule- $ kubectl delete pod sur-ssd bloque avec-derog
Validation

Réussi si vous avez vu : sur-ssd démarrer grâce au nodeSelector, bloque rester en Pending à cause de la taint, et avec-derog démarrer grâce à sa toleration. Vous maîtrisez les trois leviers de placement.

Étape 08 · Conclusion

Récapitulatif du Module 11

  • Le scheduler place les pods sur les nœuds ; on peut guider son choix.
  • nodeSelector : exiger une étiquette de nœud , le levier le plus simple.
  • Affinité / anti-affinité : préférences fines, notamment répartir des copies pour la résilience.
  • Taints & tolerations : rendre un nœud repoussant, sauf pour les pods qui ont la dérogation.
  • Kubernetes lui-même utilise une taint pour protéger le plan de contrôle (absente sur Minikube mono-nœud).
Côté résidence
On sait maintenant diriger qui habite où. Question naturelle suivante : qui a le droit de faire quoi dans la résidence, et qui peut parler à qui ? Place aux badges d'accès et aux digicodes : la sécurité.
