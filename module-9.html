Étape 01 · Séparer config et code

ConfigMaps & Secrets

Une bonne application ne contient jamais ses réglages en dur : ni l'URL de la base, ni , surtout , les mots de passe. Sinon, changer un paramètre oblige à reconstruire l'image, et les secrets traînent dans le code.

Kubernetes propose deux objets pour injecter la configuration de l'extérieur : le ConfigMap pour les réglages ordinaires, et le Secret pour les données sensibles. On les terminera en déployant une vraie application : WordPress et sa base MySQL.

Côté résidence
Le ConfigMap, ce sont les consignes affichées dans le hall : horaires, règlement, jour de sortie des poubelles , visibles de tous, sans secret. Le Secret, c'est le coffre-fort de la loge : les clés des appartements, les codes. On distribue les consignes librement ; les clés, avec précaution.
Étape 02 · Les réglages publics

ConfigMap

Un ConfigMap stocke des paires clé=valeur. On peut le créer en ligne, puis l'injecter dans un pod comme variables d'environnement ou comme fichiers.

Creer un ConfigMap en ligne de commande $ kubectl create configmap app-config \ --from-literal=COULEUR=bleu --from-literal=MODE=prod $ kubectl get configmap app-config -o yaml

Injection dans un conteneur, en variables d'environnement :

extrait d'un pod : toutes les cles deviennent des variables spec: containers: - name: app image: busybox envFrom: - configMapRef: name: app-config # COULEUR et MODE injectees
Côté résidence
On change le règlement affiché dans le hall (le ConfigMap) sans refaire l'immeuble : les occupants lisent la nouvelle consigne au prochain passage. La config vit en dehors de l'application.
Étape 03 · Les données sensibles

Secret

Un Secret ressemble à un ConfigMap, mais pour les données sensibles. Ses valeurs sont stockées en base64 (un encodage, pas un chiffrement) et bénéficient de protections supplémentaires.

Creer un secret en ligne $ kubectl create secret generic ma-cle --from-literal=password=SuperSecret La valeur apparait encodee en base64 $ kubectl get secret ma-cle -o yaml La decoder (base64 n'est PAS du chiffrement) $ echo 'U3VwZXJTZWNyZXQ=' | base64 -d

Injection dans un conteneur, clé par clé :

env: - name: DB_PASSWORD valueFrom: secretKeyRef: name: ma-cle key: password
Minikube vs Kubernetes réel
Attention au piège : par défaut, un Secret n'est qu'encodé (base64), pas chiffré. En production, on active le chiffrement au repos de la base etcd, et/ou on utilise des outils dédiés (HashiCorp Vault, Sealed Secrets, External Secrets) pour ne jamais voir un mot de passe en clair dans un fichier. Le coffre-fort doit être vraiment verrouillé, pas juste fermé.
Étape 04 · Le projet

Cap sur WordPress + MySQL

On va déployer une application réelle à deux étages, qui mobilise tout ce qu'on a appris :

MySQL (la base)

Stocke les données du site. A besoin d'un Secret (mots de passe), d'un PVC (les données doivent survivre) et d'un Service interne (ClusterIP).

WordPress (le site)

Le site web visible. Se connecte à MySQL par son nom DNS, lit le mot de passe dans le Secret, stocke ses fichiers sur un PVC, exposé en NodePort.

Le point d'orgue : WordPress trouvera MySQL via WORDPRESS_DB_HOST=mysql , c'est le DNS interne du module 7 qui fait le lien, et le même Secret sert aux deux. Tout s'emboîte.

Côté résidence
Une boutique (WordPress) et son entrepôt (MySQL). La boutique connaît l'entrepôt par son adresse (« entrepôt MySQL »), possède la clé de l'entrepôt (le Secret), et chacun a sa cave pour ne rien perdre. La boutique a pignon sur rue (NodePort) ; l'entrepôt reste à l'arrière (ClusterIP).
Étape 05 · L'entrepôt

Déployer MySQL

Le Secret partagé, puis MySQL avec son disque. Sauvegardez sous mysql.yaml.

mysql.yaml apiVersion: v1 kind: Secret metadata: { name: mysql-secret } type: Opaque stringData: # stringData = on ecrit en clair, K8s encode mysql-root-password: "RootPass123" mysql-password: "WpPass123" --- apiVersion: v1 kind: PersistentVolumeClaim metadata: { name: mysql-pvc } spec: accessModes: [ReadWriteOnce] resources: { requests: { storage: 1Gi } } --- apiVersion: apps/v1 kind: Deployment metadata: { name: mysql } spec: replicas: 1 selector: { matchLabels: { app: mysql } } template: metadata: { labels: { app: mysql } } spec: containers: - name: mysql image: mysql:8.0 env: - name: MYSQL_ROOT_PASSWORD valueFrom: { secretKeyRef: { name: mysql-secret, key: mysql-root-password } } - name: MYSQL_DATABASE value: wordpress - name: MYSQL_USER value: wpuser - name: MYSQL_PASSWORD valueFrom: { secretKeyRef: { name: mysql-secret, key: mysql-password } } ports: [{ containerPort: 3306 }] volumeMounts: - { name: data, mountPath: /var/lib/mysql } volumes: - name: data persistentVolumeClaim: { claimName: mysql-pvc } --- apiVersion: v1 kind: Service metadata: { name: mysql } spec: selector: { app: mysql } ports: [{ port: 3306 }] # ClusterIP : interne uniquement
Étape 06 · La boutique

Déployer WordPress

WordPress se branche sur MySQL par son nom et réutilise le même Secret. Sauvegardez sous wordpress.yaml.

wordpress.yaml apiVersion: v1 kind: PersistentVolumeClaim metadata: { name: wordpress-pvc } spec: accessModes: [ReadWriteOnce] resources: { requests: { storage: 1Gi } } --- apiVersion: apps/v1 kind: Deployment metadata: { name: wordpress } spec: replicas: 1 selector: { matchLabels: { app: wordpress } } template: metadata: { labels: { app: wordpress } } spec: containers: - name: wordpress image: wordpress:6.6-apache env: - name: WORDPRESS_DB_HOST value: mysql # <- le DNS interne (module 7) ! - name: WORDPRESS_DB_USER value: wpuser - name: WORDPRESS_DB_PASSWORD valueFrom: { secretKeyRef: { name: mysql-secret, key: mysql-password } } - name: WORDPRESS_DB_NAME value: wordpress ports: [{ containerPort: 80 }] volumeMounts: - { name: html, mountPath: /var/www/html } volumes: - name: html persistentVolumeClaim: { claimName: wordpress-pvc } --- apiVersion: v1 kind: Service metadata: { name: wordpress } spec: type: NodePort # expose le site a l'exterieur selector: { app: wordpress } ports: [{ port: 80, targetPort: 80 }]
Étape 07 · QCM

Vérifiez vos Acquis

QUESTION 01
Les valeurs d'un Secret sont chiffrées par défaut, donc illisibles même pour un admin du cluster.
Encodé ≠ chiffré

Par défaut, c'est du base64, décodable trivialement. Pour un vrai chiffrement : chiffrement etcd au repos, Vault, Sealed Secrets…

QUESTION 02
WordPress joint sa base via WORDPRESS_DB_HOST=mysql, qui est le nom du Service MySQL résolu par le DNS interne.
Tout s'emboîte

Le nom du Service devient un nom DNS. WordPress n'a jamais besoin de l'IP de MySQL , c'est tout l'intérêt du module 7.

QUESTION 03
On peut injecter un Secret dans un conteneur comme variable d'environnement via secretKeyRef.
Injection clé par clé

secretKeyRef pointe une clé précise du Secret vers une variable. On peut aussi monter le Secret comme fichiers.

QUESTION 04
Comme MySQL stocke ses données dans le conteneur, on n'a pas besoin de PVC pour la base.
PVC indispensable

Sans PVC, redémarrer le pod MySQL effacerait toute la base. Les données vont sur un volume persistant.

Atelier 9 : WordPress de Bout en Bout

Atelier 09 · Entièrement guidé

Déployer un site complet avec base de données

Sauvegardez mysql.yaml (étape 5) et wordpress.yaml (étape 6), puis :

1 · Déployer la base puis le site
$ kubectl apply -f mysql.yaml Attendre que MySQL soit Running avant WordPress $ kubectl get pods -w # Ctrl+C quand mysql est Running $ kubectl apply -f wordpress.yaml $ kubectl get pods,svc,pvc,secret
2 · Vérifier le coffre-fort et la connexion
Lire le secret partage (encode) $ kubectl get secret mysql-secret -o jsonpath='{.data.mysql-password}' | base64 -d ; echo Verifier que WordPress a bien demarre (pas d'erreur DB) $ kubectl logs deployment/wordpress | tail -n 20
3 · Ouvrir le site et l'installer
$ minikube service wordpress -> l'assistant d'installation WordPress s'affiche Choisir la langue, creer le compte admin, et c'est en ligne.
Validation

Réussi si l'assistant d'installation WordPress apparaît dans le navigateur et accepte la création du site (preuve que WordPress a joint MySQL via le DNS et s'est authentifié avec le Secret). Bonus persistance : supprimez le pod WordPress (kubectl delete pod -l app=wordpress), rechargez , votre site est intact. Nettoyage : kubectl delete -f wordpress.yaml -f mysql.yaml.

Étape 09 · Conclusion

Récapitulatif du Module 9

  • ConfigMap : les réglages ordinaires, injectés en variables ou fichiers, hors de l'image.
  • Secret : les données sensibles , encodées en base64, à vraiment chiffrer en production.
  • Injection : envFrom/configMapRef pour un ConfigMap, secretKeyRef pour une clé de Secret.
  • Synthèse WordPress + MySQL : Secret + PVC + Service + DNS interne, tout assemblé en une application réelle.
  • Le DNS fait le lien : WordPress trouve MySQL par son nom de Service, sans aucune IP.
Côté résidence
Notre boutique tourne, avec son entrepôt, ses clés et ses caves. Mais on l'expose encore par un NodePort un peu brut. Et si on avait dix sites ? Il faut une vraie entrée principale qui oriente chaque visiteur vers le bon service. C'est l'Ingress.
