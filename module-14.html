Étape 01 · Quand ça casse

Dépannage, CRD & HA

Dernière ligne droite. Un cluster qui tourne, c'est bien ; savoir réparer quand un pod refuse de démarrer, c'est indispensable. On verra une méthode de diagnostic systématique, puis deux sujets d'administrateur avancé : étendre Kubernetes (CRD) et garantir sa continuité (haute disponibilité).

Et pour finir : un questionnaire d'évaluation qui balaie les 4 jours.

Côté résidence
Aujourd'hui, on devient le dépanneur de la résidence : la méthode d'enquête quand une visite tourne mal, comment inventer un nouveau type de logement que la résidence ne connaissait pas, et comment s'assurer qu'il y a toujours un syndic disponible, même si l'un tombe malade.
Étape 02 · La méthode

L'Échelle du Diagnostic

Face à un problème, toujours descendre ces barreaux dans l'ordre. 95 % des pannes se révèlent dès le barreau 2 ou 3.

1. Vue d'ensemble : quel pod va mal, et dans quel etat ? $ kubectl get pods 2. Le diagnostic n.1 : les evenements en bas de la fiche $ kubectl describe pod <nom> 3. Les logs de l'application (la cause si l'appli crashe) $ kubectl logs <nom> ...et les logs du conteneur PRECEDENT s'il a deja redemarre $ kubectl logs <nom> --previous 4. Entrer dans le conteneur pour inspecter de l'interieur $ kubectl exec -it <nom> -- sh 5. Les evenements du cluster, tries par date $ kubectl get events --sort-by=.metadata.creationTimestamp
Côté résidence
L'enquête du dépanneur : d'abord regarder l'immeuble de loin (get), puis lire le registre du gardien (describe/events), puis écouter ce que dit l'occupant (logs), et seulement si besoin entrer dans l'appartement (exec). On ne défonce pas la porte au premier symptôme.
Étape 03 · Lire les symptômes

Les États d'un Pod

L'état affiché par get pods oriente directement le diagnostic :

Pending

Pas encore placé : pas assez de ressources, une taint, ou un PVC non lié. > Voir describe et les nœuds.

ImagePullBackOff

L'image est introuvable : faute de frappe dans le nom, mauvais tag, ou registre privé sans identifiants.

CrashLoopBackOff

Le conteneur démarre… puis plante, en boucle. C'est presque toujours un bug applicatif : lire logs --previous.

OOMKilled

Tué pour dépassement mémoire (la limite fixée). > Augmenter la limite ou corriger la fuite.

ContainerCreating

En cours : téléchargement de l'image ou montage d'un volume. Si ça dure, voir describe.

Running / Completed

Running = tout va bien. Completed = un Job terminé normalement (pas une erreur !).

Astuce
Le piège du débutant : confondre CrashLoopBackOff (l'appli plante > regarder les logs) et ImagePullBackOff (l'image ne se télécharge pas > vérifier le nom de l'image). Le mot dans l'état dit où chercher.
Étape 04 · Étendre Kubernetes

CRD : Inventer un Objet

Kubernetes connaît Pods, Services, Deployments… Mais on peut lui apprendre de nouveaux types d'objets via une Custom Resource Definition. L'API se met à comprendre votre vocabulaire métier.

loft-crd.yaml : on apprend a K8s le type "Loft" apiVersion: apiextensions.k8s.io/v1 kind: CustomResourceDefinition metadata: name: lofts.residence.exemple.fr spec: group: residence.exemple.fr names: { kind: Loft, plural: lofts, singular: loft } scope: Namespaced versions: - name: v1 served: true storage: true schema: openAPIV3Schema: type: object properties: spec: type: object properties: surface: { type: integer } etage: { type: integer } $ kubectl apply -f loft-crd.yaml $ kubectl get crds # 'lofts...' apparait Desormais 'Loft' est un type natif : on en cree un $ kubectl apply -f - <<'EOF' apiVersion: residence.exemple.fr/v1 kind: Loft metadata: { name: loft-atelier } spec: { surface: 90, etage: 5 } EOF $ kubectl get lofts # kubectl gere VOTRE type !
Côté résidence
Un CRD, c'est inventer un nouveau type de logement que la résidence ignorait , le « Loft » , et l'inscrire au règlement. Désormais, on peut « louer un Loft » comme on loue un appartement. Couplé à un opérateur (un robot qui surveille les Lofts et agit), c'est ainsi qu'on automatise des applications complexes.
Étape 05 · Ne jamais s'arrêter

Haute Disponibilité

Tout repose sur le plan de contrôle (l'API server, etcd…). S'il tombe, on ne peut plus piloter le cluster. La haute disponibilité (HA) consiste à le dupliquer : plusieurs nœuds de plan de contrôle, derrière un répartiteur, pour qu'il en reste toujours un debout.

Le cœur du sujet est etcd, la base qui stocke tout l'état. Elle fonctionne en quorum : il faut une majorité de membres d'accord pour décider. D'où un nombre impair (3 ou 5) : avec 3 membres, on survit à la perte d'1 ; avec 5, à la perte de 2.

Minikube vs Kubernetes réel
Notre Minikube est mono-nœud : aucune HA possible (un seul syndic, un seul immeuble). Pour simuler un cluster multi-nœuds, voire HA, en local : minikube start --nodes 3 (plusieurs immeubles) ou minikube start --ha --nodes 3 (trois syndics). En production, on déploie 3 plans de contrôle répartis sur des zones différentes, avec un load balancer devant les API servers. Le quartier ne dépend jamais d'un seul bâtiment.
Étape 06 · QCM

Vérifiez vos Acquis

QUESTION 01
CrashLoopBackOff signale une application qui démarre puis plante en boucle ; on lit les logs pour la cause.
Bug applicatif

Le conteneur se lance puis sort en erreur. kubectl logs --previous révèle généralement pourquoi.

QUESTION 02
Un CRD permet uniquement de renommer des objets existants, pas d'en créer de nouveaux types.
Vrais nouveaux types

Un CRD ajoute un type d'objet inédit à l'API, géré par kubectl comme un objet natif. C'est la base des opérateurs.

QUESTION 03
etcd fonctionne en quorum ; on déploie un nombre impair de membres (3, 5) pour survivre à des pannes.
Majorité requise

3 membres > tolère 1 panne ; 5 > tolère 2. Le nombre impair évite les égalités de vote.

QUESTION 04
Un Minikube mono-nœud offre une vraie haute disponibilité du plan de contrôle.
Un seul syndic

Avec un seul nœud, aucune redondance. La HA exige plusieurs nœuds de plan de contrôle (simulable via minikube --ha).

Étape 07 · Atelier

Atelier 14 : Casser, Diagnostiquer, Réparer

Atelier 14 · Entièrement guidé

Provoquer une panne et la résoudre par la méthode

On sabote volontairement un déploiement, puis on applique l'échelle de diagnostic. Prérequis : Minikube démarré.

1 · Provoquer la panne
Un deploiement avec une image qui n'existe pas $ kubectl create deployment casse --image=nginx:cette-version-nexiste-pas $ kubectl get pods -> etat ImagePullBackOff ou ErrImagePull
2 · Diagnostiquer
Descendre l'echelle : les evenements disent tout $ kubectl describe pod -l app=casse | grep -A5 Events -> 'Failed to pull image ... not found'
3 · Réparer
Corriger l'image vers une version valide $ kubectl set image deployment/casse nginx=nginx:1.27 $ kubectl get pods # repasse en Running Nettoyer $ kubectl delete deployment casse
Validation

Réussi si vous avez identifié la cause via describe (image introuvable) , sans deviner , puis réparé en corrigeant l'image, le pod repassant en Running. Vous savez désormais lire ce que le cluster vous dit. C'est la compétence qui distingue un opérateur d'un débutant.

Étape 08 · Évaluation finale

Questionnaire du Cursus

BILAN 01
Le mode déclaratif décrit l'état voulu ; Kubernetes le maintient en boucle (réconciliation).
Module 1

Le principe fondateur de tout Kubernetes : on décrit, il maintient.

BILAN 02
On déploie des Deployments, pas des pods nus, pour garantir le nombre de copies et les mises à jour sans coupure.
Module 5

Le Deployment maintient les réplicas et orchestre rolling updates et rollbacks.

BILAN 03
Un Service donne une adresse et un nom DNS stables devant des pods éphémères.
Module 7

L'adresse fixe + CoreDNS : on communique par nom, jamais par IP.

BILAN 04
Les données qui doivent survivre vont sur un PVC ; un Secret n'est qu'encodé en base64 par défaut.
Modules 8 & 9

Persistance via PVC ; sécuriser vraiment les secrets en production (chiffrement, Vault…).

BILAN 05
Un DaemonSet déploie un nombre fixe de réplicas réparti aléatoirement, comme un Deployment.
Module 6

Non : un DaemonSet place exactement un pod par nœud (ex. node-exporter). Le nombre suit les nœuds.

BILAN 06
Une ressource Ingress route le trafic même sans contrôleur, et Minikube en a un actif par défaut.
Module 10

Double erreur : il faut un contrôleur, et sur Minikube on l'active (addons enable ingress).

Étape 09 · Fin du cursus

La Résidence est Livrée

En quatre jours, vous avez construit et administré une résidence complète : des immeubles (nœuds) gérés par un syndic (plan de contrôle), des appartements (pods) tenus par un contrat (Deployment), des adresses (Services), un annuaire (DNS), des caves (volumes), un coffre-fort (Secrets), un hall d'accueil (Ingress), des capteurs (supervision), des badges (RBAC), des meubles clé en main (Helm) et la trousse du dépanneur.

Surtout, vous avez compris la différence permanente : Minikube est notre maquette grandeur réelle sur une machine ; tout ce que vous avez écrit , chaque fichier YAML, chaque commande , fonctionne à l'identique sur un vrai cluster de production.

Pour aller plus loin
Refaites les ateliers jusqu'à ce que les commandes deviennent un réflexe. Puis passez à un vrai cluster (multi-nœuds via minikube --nodes, ou un cluster cloud) pour voir la métaphore prendre toute sa taille. La certification CKA est une suite naturelle. La résidence est à vous : habitez-la.
