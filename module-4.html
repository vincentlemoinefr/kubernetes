Étape 01 · La brique de base

Les Pods en Profondeur

Le pod est la plus petite chose que Kubernetes sait gérer. C'est l'appartement : une enveloppe qui contient un ou plusieurs conteneurs partageant la même adresse réseau et le même espace de stockage local.

Point clé déjà vu : on ne manipule jamais un conteneur seul. Si un appartement n'a qu'un habitant (le cas courant), on déploie quand même un pod. Pourquoi cette enveloppe ? Parce qu'elle donne aux conteneurs un endroit commun pour vivre : même IP, même localhost, possibilité de partager des fichiers.

Ce module ouvre l'appartement en grand : comment on le décrit, son cycle de vie, ses colocataires, et comment on vérifie qu'il est en bonne santé.

Côté résidence
Un pod, c'est un appartement avec une seule porte d'entrée (une IP) et une seule boîte aux lettres. Les conteneurs qui y vivent sont des colocataires : ils partagent l'adresse et peuvent se passer des plats par-dessus la table (localhost), mais chacun a sa chambre.
Étape 02 · La langue officielle

Le Manifeste YAML

Un pod se décrit dans un fichier YAML avec toujours les mêmes quatre sections. Apprenez-les une fois : tous les objets Kubernetes suivent ce squelette.

apiVersion: v1 # la version de l'API (ici, le groupe de base) kind: Pod # le TYPE d'objet qu'on cree metadata: # l'identite : nom et etiquettes name: web labels: app: web spec: # la SPECIFICATION : ce qu'on veut vraiment containers: - nom + image + port de l'unique conteneur - name: nginx image: nginx:1.25 ports: - containerPort: 80
Côté résidence
kind = « c'est un appartement ». metadata = le nom sur la sonnette et les étiquettes. spec = le cahier des charges : qui habite (image), par quelle porte on entre (port). L'apiVersion indique juste quel service de la mairie traite ce type de demande.
Étape 03 · Impératif vs déclaratif

Créer un Pod, Deux Façons

La méthode impérative (rapide, pour tester) et la méthode déclarative (un fichier, la vraie bonne pratique). Les deux mènent au même appartement.

=== Imperatif : une commande, pas de fichier === $ kubectl run web --image=nginx:1.25 Astuce : generer le YAML sans rien creer (--dry-run + -o yaml) $ kubectl run web --image=nginx:1.25 --dry-run=client -o yaml > pod.yaml === Declaratif : on ecrit pod.yaml, puis on l'applique === $ kubectl apply -f pod.yaml Re-appliquer le meme fichier ne casse rien : Kubernetes reconcilie $ kubectl apply -f pod.yaml # "unchanged" Supprimer ce que decrit le fichier $ kubectl delete -f pod.yaml
Kubernetes réel
En production, on n'utilise quasiment que le déclaratif : les fichiers YAML sont la mémoire écrite du cluster, versionnés dans Git. L'impératif sert à explorer ou dépanner. Le --dry-run -o yaml est le meilleur ami du débutant : il génère un squelette correct qu'on n'a plus qu'à ajuster.
Étape 04 · La vie d'un appartement

Cycle de Vie & restartPolicy

Un pod traverse des phases, visibles dans la colonne STATUS. Les connaître, c'est savoir lire ce qui se passe.

Pending

Accepté mais pas encore démarré : image en cours de téléchargement, ou en attente d'un immeuble.

Running

Au moins un conteneur tourne. L'état que l'on vise pour un service.

Succeeded / Failed

Le conteneur a terminé : avec succès (code 0) ou en échec. Typique des tâches ponctuelles.

La restartPolicy du pod décide quoi faire quand un conteneur s'arrête : Always (toujours relancer , défaut, pour un service), OnFailure (relancer seulement en cas d'échec), Never (ne jamais relancer). Si un conteneur boucle en plantant, vous verrez le statut CrashLoopBackOff : Kubernetes le relance, mais espace de plus en plus les tentatives.

Côté résidence
CrashLoopBackOff = un habitant qui s'évanouit dès qu'on le relève. Le gardien le réanime, encore et encore, mais attend de plus en plus longtemps entre deux essais pour ne pas s'épuiser. C'est un signal : il faut regarder pourquoi il tombe (les logs).
Étape 05 · Colocataires & travaux

Multi-Conteneurs & Init

Un pod peut héberger plusieurs conteneurs (motif « sidecar » : un conteneur principal + un assistant) et lancer des initContainers qui s'exécutent avant, jusqu'au bout, dans l'ordre.

spec: initContainers: # les "ouvriers" : tournent AVANT, puis partent - name: preparation image: busybox:1.36 command: ['sh', '-c', 'echo prepa && sleep 3'] containers: # les "colocataires" : tournent ensemble - name: web image: nginx:1.25 - name: assistant # sidecar : ex. collecte de logs image: busybox:1.36 command: ['sh','-c','while true; do echo tick; sleep 5; done']
Côté résidence
Les initContainers sont les ouvriers qui peignent les murs et branchent l'eau avant l'emménagement : ils finissent leur travail, puis s'en vont. Les containers sont les colocataires permanents qui vivent ensemble dans l'appartement et partagent la cuisine.
Étape 06 · Le médecin & le panneau

Les Sondes (Probes)

Comment Kubernetes sait-il qu'un conteneur va bien ? Avec des sondes qui l'interrogent régulièrement. Trois types, trois rôles distincts.

♥

livenessProbe

« Es-tu vivant ? » Si la réponse cesse, Kubernetes redémarre le conteneur.

le médecin
⊙

readinessProbe

« Es-tu prêt à recevoir du monde ? » Si non, on coupe le trafic vers lui (sans le tuer).

panneau ouvert/fermé
⏱

startupProbe

Délai de grâce pour les démarrages lents : tant qu'elle n'a pas réussi, les autres sondes attendent.

le réveil en douceur
livenessProbe: # interroge GET / sur le port 80 httpGet: { path: /, port: 80 } initialDelaySeconds: 5 # attendre 5s avant la 1ere verif periodSeconds: 10 # puis verifier toutes les 10s readinessProbe: httpGet: { path: /, port: 80 } periodSeconds: 5
Étape 07 · Réservation & plafond

Ressources : requests & limits

On précise au syndic combien de ressources un conteneur réserve et combien il a le droit de consommer au maximum. Deux notions :

requests , la réservation garantie. Le scheduler s'en sert pour choisir un immeuble qui a vraiment la place. limits , le plafond. Dépasser la limite mémoire = expulsion immédiate (OOMKilled) ; dépasser la limite CPU = simple ralentissement.

resources: requests: # garanti / sert au placement memory: "64Mi" cpu: "100m" # 100m = 0,1 coeur de CPU limits: # plafond a ne pas depasser memory: "128Mi" cpu: "200m"
Côté résidence
requests = la surface réservée au bail, que l'agent immobilier garantit avant d'attribuer l'appartement. limits = le plafond de consommation : trop d'eau, on coupe ; trop de bruit, on expulse. Sans requests, l'agent loge à l'aveugle et peut surcharger un immeuble.
Étape 08 · QCM

Vérifiez vos Acquis

QUESTION 01
Les conteneurs d'un même pod partagent l'adresse IP et peuvent se parler via localhost.
Colocataires

Oui : un pod = un réseau partagé. C'est tout l'intérêt de l'enveloppe pod par rapport à des conteneurs isolés.

QUESTION 02
La readinessProbe redémarre le conteneur quand elle échoue.
Confusion fréquente

Non : c'est la livenessProbe qui redémarre. La readinessProbe coupe seulement le trafic, sans tuer le conteneur.

QUESTION 03
Les initContainers s'exécutent jusqu'à la fin, dans l'ordre, avant que les conteneurs principaux démarrent.
Les ouvriers d'abord

Exact. Idéal pour préparer le terrain (attendre une base de données, télécharger un fichier) avant l'emménagement.

QUESTION 04
Dépasser la limite mémoire d'un conteneur provoque sa terminaison (OOMKilled).
Plafond mémoire strict

Oui. La mémoire ne se « ralentit » pas : au-delà de la limite, le conteneur est tué. Le CPU, lui, est seulement bridé.

Étape 09 · Atelier

Atelier 4 : un Appartement Complet

Atelier 04 · Entièrement guidé

Un pod avec init, sonde et ressources, observé en direct

On crée un appartement réaliste : un ouvrier qui prépare, un serveur web surveillé par une sonde, et des ressources cadrées. Copiez le fichier, appliquez, observez.

1. Écrire le manifeste (copier-coller dans un terminal)
$ cat > pod-complet.yaml <<'EOF' apiVersion: v1 kind: Pod metadata: name: app-complet labels: { app: demo } spec: initContainers: - name: preparation image: busybox:1.36 command: ['sh','-c','echo "Prepa..." && sleep 5'] containers: - name: web image: nginx:1.25 ports: [{ containerPort: 80 }] readinessProbe: httpGet: { path: /, port: 80 } initialDelaySeconds: 3 resources: requests: { memory: "64Mi", cpu: "100m" } limits: { memory: "128Mi", cpu: "200m" } EOF
2. Appliquer et observer le cycle de vie
$ kubectl apply -f pod-complet.yaml Suivre en direct : Init -> PodInitializing -> Running $ kubectl get pod app-complet -w # Ctrl+C pour stopper Voir le detail des conteneurs et les events $ kubectl describe pod app-complet Lire les logs de l'ouvrier, puis du serveur web $ kubectl logs app-complet -c preparation $ kubectl logs app-complet -c web
Validation & nettoyage

Réussi si vous avez vu le statut passer par Init (les 5 secondes de l'ouvrier) avant Running, et si describe montre la readinessProbe et les ressources. Nettoyez : kubectl delete -f pod-complet.yaml.

Étape 10 · Conclusion

Récapitulatif du Module 4

  • Le pod = l'appartement : un ou plusieurs conteneurs partageant IP, localhost et stockage local.
  • Le squelette YAML : apiVersion, kind, metadata, spec , commun à tous les objets.
  • Cycle de vie : Pending > Running > Succeeded/Failed, et la restartPolicy (gare au CrashLoopBackOff).
  • Init + sidecar : les ouvriers tournent avant ; les colocataires tournent ensemble.
  • Santé & ressources : liveness (redémarre), readiness (coupe le trafic), requests (réserve), limits (plafond).
Côté résidence
Un pod tout seul reste fragile : si l'appartement brûle, personne ne le reconstruit. C'est tout l'objet du module suivant : un contrat de gestion qui garantit que les appartements restent occupés, quoi qu'il arrive.
