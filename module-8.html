Étape 01 · L'éphémère

Volumes & Stockage

Un conteneur a un système de fichiers… jetable. Quand le pod redémarre, tout ce qui a été écrit à l'intérieur disparaît. Pour un serveur web sans état, peu importe. Pour une base de données, c'est une catastrophe.

La solution : les volumes. Un volume est un espace de stockage monté dans le conteneur, mais dont la durée de vie est découplée de celle du conteneur. On va voir une gradation, du plus éphémère au plus durable.

Côté résidence
Quand un locataire part, l'appartement est vidé : ses affaires laissées dans l'appart disparaissent. Mais ce qu'il range à la cave (le volume) reste, et le prochain occupant le retrouve. La cave survit aux déménagements ; l'appartement, non.
Étape 02 · Volumes simples

emptyDir & hostPath

Deux volumes de base, à connaître pour comprendre les limites qui mènent aux PersistentVolumes :

emptyDir

Un dossier vide, partagé entre les conteneurs d'un même pod. Survit au redémarrage d'un conteneur, mais disparaît si le pod est supprimé. Utile comme cache ou échange entre conteneurs.

hostPath

Monte un dossier de la machine hôte dans le pod. Survit au pod, mais lié à un nœud précis : si le pod est replacé ailleurs, il ne retrouve plus ses données. Fragile en multi-nœuds.

Exemple d'emptyDir partagé entre deux conteneurs :

extrait d'un pod spec: containers: - name: ecrivain image: busybox volumeMounts: - { name: partage, mountPath: /data } - name: lecteur image: busybox volumeMounts: - { name: partage, mountPath: /data } volumes: - name: partage emptyDir: {} # dossier ephemere commun
Minikube vs Kubernetes réel
hostPath fonctionne « bien » sur Minikube justement parce qu'il n'y a qu'un nœud : le pod retombe toujours sur le même immeuble, donc sur la même cave. Sur un vrai cluster, c'est un piège : le pod peut renaître sur un autre immeuble et perdre l'accès. D'où la nécessité d'un vrai stockage abstrait : le PersistentVolume.
Étape 03 · Le bon modèle

PersistentVolume & Claim

Le vrai stockage durable sépare deux rôles, comme une offre et une demande :

01

PersistentVolume (PV)

Un morceau de stockage réel dans le cluster (un disque). Géré par l'admin ou créé à la demande. L'offre.

02

PersistentVolumeClaim (PVC)

La demande d'un développeur : « j'ai besoin de 1 Go ». Kubernetes l'associe à un PV qui convient. La demande.

03

StorageClass

L'usine à PV : crée automatiquement un PV quand un PVC arrive. Le provisionnement « à la demande ».

Côté résidence
Le PV est un box de stockage physique loué à la résidence. Le PVC est le bon de réservation que vous remplissez (« je veux un box de 5 m³ »). La StorageClass est l'entreprise de box qui en construit un neuf dès qu'une réservation arrive, sans intervention humaine.
Étape 04 · La demande

Créer un PVC

Bonne nouvelle : Minikube fournit déjà une StorageClass par défaut (standard). On n'a donc qu'à écrire la demande (PVC) ; le PV se crée tout seul.

Voir l'usine a stockage fournie par Minikube $ kubectl get storageclass data-pvc.yaml : la demande de 1 Go apiVersion: v1 kind: PersistentVolumeClaim metadata: name: data-pvc spec: accessModes: - ReadWriteOnce # monte par un seul noeud a la fois resources: requests: storage: 1Gi $ kubectl apply -f data-pvc.yaml Le PVC est 'Bound' = un PV a ete cree et associe automatiquement $ kubectl get pvc $ kubectl get pv # le PV ne par la StorageClass
Étape 05 · Démonstration

nginx avec une Page Persistante

Branchons ce PVC sur un nginx, à l'endroit où il sert ses pages (/usr/share/nginx/html). On écrira une page web : elle devra survivre à la destruction du pod.

web-persistant.yaml apiVersion: apps/v1 kind: Deployment metadata: name: web spec: replicas: 1 selector: { matchLabels: { app: web } } template: metadata: { labels: { app: web } } spec: containers: - name: nginx image: nginx:1.27 volumeMounts: - name: contenu mountPath: /usr/share/nginx/html # la cave montee ici volumes: - name: contenu persistentVolumeClaim: claimName: data-pvc # notre box reserve --- apiVersion: v1 kind: Service metadata: { name: web } spec: type: NodePort selector: { app: web } ports: [{ port: 80, targetPort: 80 }]
Étape 06 · QCM

Vérifiez vos Acquis

QUESTION 01
Ce qu'un conteneur écrit dans son système de fichiers est conservé après suppression du pod.
Système jetable

Tout ce qui est écrit hors d'un volume disparaît avec le pod. Pour persister, il faut un volume (et pour durer vraiment, un PVC).

QUESTION 02
Un emptyDir survit au redémarrage d'un conteneur mais disparaît si le pod est supprimé.
Lié au pod

La durée de vie d'emptyDir est celle du pod. Utile pour du cache ou pour partager entre conteneurs d'un même pod.

QUESTION 03
Le PVC est la « demande » de stockage, et la StorageClass peut créer le PV automatiquement.
Offre / demande

PVC = bon de réservation ; StorageClass = usine qui fabrique le box (PV) à la demande. Minikube en fournit une par défaut.

QUESTION 04
hostPath est un choix robuste pour des données critiques sur un cluster multi-nœuds.
Piège en production

hostPath lie les données à un nœud précis. Si le pod renaît ailleurs, il perd l'accès. On utilise un PVC adossé à un stockage réseau.

Étape 07 · Atelier

Atelier 8 : Prouver la Persistance

Atelier 08 · Entièrement guidé

Écrire une page, détruire le pod, la retrouver intacte

Sauvegardez data-pvc.yaml (étape 4) et web-persistant.yaml (étape 5), puis :

1 · Déployer le stockage et l'appli
$ kubectl apply -f data-pvc.yaml $ kubectl apply -f web-persistant.yaml $ kubectl get pvc,pods
2 · Écrire une page web DANS le volume
Recuperer le nom du pod dans une variable $ POD=$(kubectl get pod -l app=web -o name) Ecrire un index.html dans la cave montee $ kubectl exec $POD -- sh -c 'echo "<h1>Ma page survit aux deces de pod !</h1>" > /usr/share/nginx/html/index.html' Verifier dans le navigateur $ minikube service web
3 · Détruire le pod et vérifier
Tuer le pod : le Deployment en recree un neuf, sur le MEME PVC $ kubectl delete $POD $ kubectl get pods # un nouveau pod apparait Rouvrir : la page personnalisee est TOUJOURS la $ minikube service web
Validation

Réussi si, après avoir supprimé le pod, le nouveau pod sert toujours votre page « Ma page survit… ». Vous venez de prouver que les données vivent dans la cave (le PVC), pas dans l'appartement (le pod). Nettoyage : kubectl delete -f web-persistant.yaml -f data-pvc.yaml.

Étape 08 · Conclusion

Récapitulatif du Module 8

  • Le système de fichiers d'un conteneur est jetable : hors volume, tout disparaît avec le pod.
  • emptyDir : partagé dans un pod, éphémère. hostPath : sur le nœud, fragile en multi-nœuds.
  • Le bon modèle : PVC (la demande) + StorageClass (l'usine) > PV (le disque réel).
  • Minikube fournit une StorageClass par défaut : on écrit juste le PVC, le PV est créé tout seul.
  • Prouvé en pratique : les données survivent à la destruction du pod.
Côté résidence
Nos applis peuvent désormais stocker durablement. Reste un sujet sensible : comment leur transmettre des réglages et surtout des mots de passe proprement ? Les consignes au tableau d'affichage, et le coffre-fort. Place à WordPress et sa base de données.
