Étape 01 · Un pod partout

DaemonSets & Supervision

Jusqu'ici, un Deployment place N copies n'importe où. Mais certains besoins sont différents : on veut exactement un pod sur chaque nœud, ni plus ni moins. C'est le rôle du DaemonSet.

Exemples typiques : un agent de logs, un agent réseau, ou , ce qui nous intéresse , un capteur de métriques sur chaque machine. On va s'en servir pour bâtir le socle de supervision de la formation : Node Exporter + Prometheus + Grafana.

Côté résidence
Un DaemonSet, c'est le détecteur de fumée installé dans chaque immeuble : pas « 3 détecteurs quelque part », mais un par immeuble, automatiquement. Quand on construit un nouvel immeuble, son détecteur s'installe tout seul.
Étape 02 · La différence

DaemonSet vs Deployment

Même famille, logique opposée sur le placement. À choisir selon la question : « combien de copies, et où ? »

Deployment

« Je veux N copies, peu importe où. » Le scheduler les répartit. Pour les applications classiques (web, API).

DaemonSet

« Je veux une copie par nœud. » Pas de nombre à fixer : il suit le nombre de nœuds. Pour les agents système.

Kubernetes lui-même utilise des DaemonSets : kube-proxy et le plugin réseau (CNI) tournent ainsi sur chaque nœud. Vérifions-le :

Les DaemonSets internes, tous namespaces $ kubectl get daemonsets -A Sur Minikube : kube-proxy est un DaemonSet (1 pod, car 1 noeud) $ kubectl get pods -n kube-system -l k8s-app=kube-proxy -o wide
Minikube vs Kubernetes réel
Sur notre Minikube mono-nœud, un DaemonSet = 1 seul pod (1 immeuble). Sur un cluster de 50 nœuds, le même DaemonSet déploie automatiquement 50 pods, un par immeuble. Le YAML est rigoureusement identique : seule la taille du quartier change.
Étape 03 · L'architecture de supervision

Le Trio de la Surveillance

Notre socle d'observabilité (qu'on garde toute la formation) repose sur trois briques aux rôles complémentaires :

01

Node Exporter

Un DaemonSet. Sur chaque nœud, il expose CPU, RAM, disque, réseau au format que Prometheus comprend. Le capteur.

02

Prometheus

Un Deployment. Il interroge (« scrape ») les capteurs toutes les 15 s et stocke les mesures dans le temps. Le collecteur.

03

Grafana

Un Deployment. Il lit Prometheus et dessine des tableaux de bord lisibles. L'écran de contrôle.

Côté résidence
Node Exporter = les capteurs dans chaque immeuble (température, conso électrique). Prometheus = le PC de sécurité qui relève tous les capteurs en boucle et garde l'historique. Grafana = les écrans muraux de la loge qui affichent tout joliment pour le gardien.
Étape 04 · Le capteur

Node Exporter (DaemonSet)

On range tout dans un namespace monitoring. Voici le capteur : un DaemonSet (un pod par nœud) plus un Service pour que Prometheus le joigne par un nom stable. Sauvegardez ce fichier sous node-exporter.yaml.

node-exporter.yaml apiVersion: apps/v1 kind: DaemonSet metadata: name: node-exporter namespace: monitoring spec: selector: matchLabels: { app: node-exporter } template: metadata: labels: { app: node-exporter } spec: hostNetwork: true # voit le reseau reel du noeud hostPID: true containers: - name: node-exporter image: prom/node-exporter:v1.8.2 args: ["--path.rootfs=/host"] ports: - containerPort: 9100 volumeMounts: - name: rootfs mountPath: /host readOnly: true volumes: - name: rootfs hostPath: { path: / } --- apiVersion: v1 kind: Service metadata: name: node-exporter namespace: monitoring labels: { app: node-exporter } spec: selector: { app: node-exporter } ports: - name: metrics port: 9100 targetPort: 9100
Étape 05 · Le collecteur

Prometheus (Config + Deployment)

Prometheus a besoin d'un fichier de config (quelles cibles scraper). On le fournit via un ConfigMap (module 9), monté dans le pod. Sauvegardez sous prometheus.yaml.

prometheus.yaml apiVersion: v1 kind: ConfigMap metadata: name: prometheus-config namespace: monitoring data: prometheus.yml: | global: scrape_interval: 15s scrape_configs: - job_name: 'prometheus' static_configs: - targets: ['localhost:9090'] - job_name: 'node-exporter' static_configs: - targets: ['node-exporter:9100'] # le Service ci-dessus --- apiVersion: apps/v1 kind: Deployment metadata: name: prometheus namespace: monitoring spec: replicas: 1 selector: { matchLabels: { app: prometheus } } template: metadata: { labels: { app: prometheus } } spec: containers: - name: prometheus image: prom/prometheus:v2.54.1 ports: [{ containerPort: 9090 }] volumeMounts: - name: config mountPath: /etc/prometheus volumes: - name: config configMap: { name: prometheus-config } --- apiVersion: v1 kind: Service metadata: name: prometheus namespace: monitoring spec: type: NodePort selector: { app: prometheus } ports: [{ port: 9090, targetPort: 9090 }]
Étape 06 · L'écran

Grafana (avec source pré-câblée)

Pour éviter tout réglage manuel, on pré-branche Prometheus dans Grafana via un ConfigMap de provisioning. Sauvegardez sous grafana.yaml.

grafana.yaml apiVersion: v1 kind: ConfigMap metadata: name: grafana-datasources namespace: monitoring data: datasource.yaml: | apiVersion: 1 datasources: - name: Prometheus type: prometheus access: proxy url: http://prometheus:9090 isDefault: true --- apiVersion: apps/v1 kind: Deployment metadata: name: grafana namespace: monitoring spec: replicas: 1 selector: { matchLabels: { app: grafana } } template: metadata: { labels: { app: grafana } } spec: containers: - name: grafana image: grafana/grafana:11.2.0 ports: [{ containerPort: 3000 }] env: - name: GF_SECURITY_ADMIN_PASSWORD value: "admin" # mot de passe d'apprentissage volumeMounts: - name: ds mountPath: /etc/grafana/provisioning/datasources volumes: - name: ds configMap: { name: grafana-datasources } --- apiVersion: v1 kind: Service metadata: name: grafana namespace: monitoring spec: type: NodePort selector: { app: grafana } ports: [{ port: 3000, targetPort: 3000 }]
Étape 07 · La voie de production

En Vrai : kube-prometheus-stack

Nos manifestes manuels sont parfaits pour comprendre les rouages : on voit le capteur, le collecteur, l'écran et comment ils se branchent. C'est l'objectif pédagogique.

En production, personne n'écrit ces YAML à la main. On installe le tout via Helm (module 13) avec un seul paquet officiel, kube-prometheus-stack, qui ajoute en bonus : Alertmanager, des dizaines de dashboards prêts, et la découverte automatique des cibles.

Aperçu (on le fera vraiment au module 13) $ helm repo add prometheus-community https://prometheus-community.github.io/helm-charts $ helm install kube-prom prometheus-community/kube-prometheus-stack \ --namespace monitoring --create-namespace
Minikube vs Kubernetes réel
Notre Prometheus scrape le capteur via une cible statique (node-exporter:9100) : ça marche car il n'y a qu'un nœud. Sur un grand cluster, on n'écrit pas la liste à la main : Prometheus découvre tout seul les capteurs via l'API Kubernetes (service discovery). C'est exactement ce que kube-prometheus-stack configure pour vous.
Étape 08 · QCM

Vérifiez vos Acquis

QUESTION 01
Un DaemonSet garantit un pod par nœud et déploie tout seul un pod sur chaque nouveau nœud ajouté.
Un capteur par immeuble

C'est sa définition. On ne fixe pas de nombre de réplicas : il suit le nombre de nœuds, automatiquement.

QUESTION 02
C'est Grafana qui collecte et stocke les métriques dans le temps.
Rôles distincts

Prometheus collecte et stocke. Grafana ne fait que lire Prometheus pour l'afficher. Node Exporter, lui, expose les mesures brutes.

QUESTION 03
Sur un Minikube mono-nœud, le DaemonSet node-exporter ne crée qu'un seul pod.
Un nœud, un pod

Un seul immeuble > un seul capteur. Le même YAML créerait 50 pods sur un cluster de 50 nœuds.

QUESTION 04
Prometheus doit obligatoirement découvrir ses cibles via l'API ; on ne peut pas lui donner une liste fixe.
Les deux existent

La cible statique (notre cas) est valide et simple. La découverte automatique est juste plus pratique à grande échelle.

Étape 09 · Atelier

Atelier 6 : Déployer le Socle de Supervision

Atelier 06 · Entièrement guidé

Du capteur à l'écran, en 5 minutes

Sauvegardez les trois fichiers des étapes 4, 5 et 6 (node-exporter.yaml, prometheus.yaml, grafana.yaml) dans un même dossier, puis :

1 · Créer le namespace et tout déployer
$ kubectl create namespace monitoring $ kubectl apply -f node-exporter.yaml $ kubectl apply -f prometheus.yaml $ kubectl apply -f grafana.yaml Attendre que les 3 pods soient Running $ kubectl get pods -n monitoring -w # Ctrl+C pour sortir
2 · Ouvrir Prometheus et vérifier les cibles
Ouvre Prometheus dans le navigateur $ minikube service prometheus -n monitoring Dans l'interface : menu Status > Targets -> les jobs 'prometheus' et 'node-exporter' doivent etre 'UP'
3 · Ouvrir Grafana et afficher un tableau de bord
$ minikube service grafana -n monitoring Connexion : utilisateur 'admin' / mot de passe 'admin' La source Prometheus est deja branchee. Importer un dashboard : Menu Dashboards > New > Import > coller l'ID 1860 > Load -> choisir la source 'Prometheus' > Import
Validation

Réussi si Prometheus affiche ses deux cibles en UP, et si le dashboard 1860 (« Node Exporter Full ») dans Grafana montre des courbes vivantes de CPU, RAM et disque de votre machine. Vous avez un socle de supervision opérationnel, qu'on réutilisera. Pour tout retirer : kubectl delete namespace monitoring.

Étape 10 · Conclusion

Récapitulatif du Module 6

  • DaemonSet : un pod par nœud, automatiquement , pour les agents système (logs, réseau, métriques).
  • Le trio d'observabilité : Node Exporter (capteur) > Prometheus (collecteur) > Grafana (écran).
  • Node Exporter est un DaemonSet ; Prometheus et Grafana sont des Deployments.
  • On a relié les briques via Services, ConfigMaps et un provisioning de source , toutes les notions à venir, déjà à l'œuvre.
  • En prod : on installe tout via Helm (kube-prometheus-stack) plutôt qu'à la main.
Côté résidence
La résidence a maintenant ses capteurs, son PC de sécurité et ses écrans. On a remarqué un détail crucial : tout le monde se joint par un nom stable (prometheus, node-exporter), jamais par une adresse. C'est l'objet du prochain module : les Services et le DNS.
