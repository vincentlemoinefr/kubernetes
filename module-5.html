Étape 01 · Le besoin

Déploiements & Échelle

Au module 4, on a créé des pods. Mais un pod tout seul a un défaut fatal : s'il meurt, personne ne le remplace. Pire, on ne peut pas en demander « 5 copies » d'un coup. Le pod est une brique, pas une stratégie.

La solution s'appelle le Deployment. On ne crée presque jamais de pods à la main en vrai : on crée des Deployments, qui eux gèrent les pods pour nous, en boucle, selon le principe déclaratif vu au module 1.

Côté résidence
Un appartement loué directement par vous, c'est risqué : si le locataire part, l'appartement reste vide. Le Deployment, c'est un contrat de gestion locative confié au syndic : « maintiens en permanence 5 appartements loués à l'appli X ». Un locataire part > le syndic en reloge un, automatiquement.
Étape 02 · La hiérarchie

Deployment > ReplicaSet > Pod

Quand vous créez un Deployment, trois objets s'empilent. Comprendre qui gère qui évite 90 % des confusions :

01

Deployment

Le contrat que vous écrivez. Il décrit l'appli, le nombre de copies voulu et la stratégie de mise à jour.

02

ReplicaSet

Créé automatiquement par le Deployment. Son seul travail : garantir le bon nombre de pods identiques. Un par version.

03

Pod

Créés par le ReplicaSet. Ce sont les copies réelles de l'appli qui tournent. Jetables et remplaçables.

À retenir : vous ne touchez qu'au Deployment. Le ReplicaSet et les pods sont gérés pour vous. Lors d'une mise à jour, le Deployment crée un nouveau ReplicaSet et vide l'ancien progressivement.

Côté résidence
Vous signez un contrat (Deployment) avec le syndic. Le syndic mandate un gestionnaire (ReplicaSet) chargé de garder 5 appartements loués (Pods). Vous ne parlez qu'au contrat ; le reste se fait en coulisses.
Étape 03 · Création

Créer un Deployment

Deux façons : la rapide (impérative) pour tester, et la propre (déclarative, un fichier YAML) pour la vraie vie. Apprenez les deux.

--- Voie rapide : imperative (pratique pour bricoler) --- $ kubectl create deployment web --image=nginx --replicas=3 Observer les 3 etages de la hierarchie $ kubectl get deployments $ kubectl get replicasets $ kubectl get pods --show-labels Detail complet d'un deployment (evenements en bas) $ kubectl describe deployment web

La voie propre : un fichier web-deploy.yaml versionnable, relisible, partageable.

web-deploy.yaml apiVersion: apps/v1 kind: Deployment metadata: name: web spec: replicas: 3 selector: matchLabels: app: web # le RS adopte les pods portant ce label template: # le moule a pods metadata: labels: app: web # DOIT correspondre au selector ci-dessus spec: containers: - name: nginx image: nginx:1.27 ports: - containerPort: 80 $ kubectl apply -f web-deploy.yaml # cree OU met a jour, idempotent
Étape 04 · L'art des étiquettes

Labels & Sélecteurs

Les labels sont des étiquettes clé=valeur collées sur les objets. C'est le ciment de tout Kubernetes : le ReplicaSet retrouve « ses » pods par leur label, et plus tard les Services trouveront les bons pods de la même façon.

Lister en affichant les etiquettes $ kubectl get pods --show-labels Filtrer par etiquette (= selecteur) $ kubectl get pods -l app=web Ajouter / changer une etiquette a la volee $ kubectl label pod <nom-du-pod> tier=frontend Tout ce qui porte app=web, d'un coup $ kubectl get all -l app=web
Côté résidence
Les labels sont les étiquettes sur les boîtes aux lettres : « entreprise=web », « étage=2 ». Le gestionnaire ne connaît pas ses appartements par leur numéro, mais par leur étiquette. Changez l'étiquette, et l'appartement « change d'équipe » sans déménager.
Étape 05 · Cloisonner

Les Namespaces

Un namespace découpe le cluster en zones logiques isolées. Deux apps « web » peuvent coexister dans deux namespaces sans se gêner. C'est l'unité d'organisation et de quotas.

Les namespaces existants (kube-system = les composants internes) $ kubectl get namespaces Creer un namespace de travail $ kubectl create namespace atelier Agir dans un namespace precis : l'option -n $ kubectl get pods -n atelier $ kubectl create deployment web --image=nginx -n atelier Eviter de retaper -n partout : changer le namespace par defaut $ kubectl config set-context --current --namespace=atelier Tout voir, tous namespaces confondus : -A $ kubectl get pods -A
Côté résidence
Un namespace est une aile (ou un étage) de la résidence : l'aile « production », l'aile « test ». Chaque aile a ses appartements, ses règles, son budget. On peut avoir un appartement « web » dans deux ailes différentes sans confusion.
Étape 06 · Mettre à jour sans coupure

Rolling Update & Rollback

Le superpouvoir du Deployment : changer de version sans fermer le service. Kubernetes remplace les pods un par un (rolling update). Et si la nouvelle version est buggée, on revient en arrière en une commande.

Mettre a jour l'image : declenche un remplacement progressif $ kubectl set image deployment/web nginx=nginx:1.28 Suivre le deroulement en direct $ kubectl rollout status deployment/web Historique des versions deployees $ kubectl rollout history deployment/web Catastrophe ? Retour a la version precedente, immediat $ kubectl rollout undo deployment/web Revenir a une revision precise $ kubectl rollout undo deployment/web --to-revision=1
Côté résidence
Rénover sans vider l'immeuble : on refait un appartement à la fois. Pendant que le 1er est en travaux, les autres restent loués. Si la nouvelle déco est ratée, le gestionnaire restaure le plan précédent instantanément, appartement par appartement.
Étape 07 · Grandir tout seul

Autoscaling (HPA)

Jusqu'ici, on change le nombre de copies à la main (kubectl scale). Le Horizontal Pod Autoscaler le fait automatiquement selon la charge CPU. Il a besoin de metrics-server pour mesurer la consommation.

Prerequis : activer metrics-server (le capteur de charge) $ minikube addons enable metrics-server Verifier qu'on lit bien le CPU/RAM des pods (patienter 1 min) $ kubectl top pods Mise a l'echelle manuelle (le point de depart) $ kubectl scale deployment web --replicas=5 Mise a l'echelle AUTOMATIQUE : entre 1 et 10 copies, cible 50% CPU $ kubectl autoscale deployment web --cpu-percent=50 --min=1 --max=10 $ kubectl get hpa # suivre la decision de l'autoscaler
Minikube vs Kubernetes réel
Le HPA fonctionne pareil partout. La différence : sur Minikube, l'autoscaler crée plus de pods sur l'unique nœud (jusqu'à saturer sa RAM). En production, un second mécanisme , le Cluster Autoscaler , ajoute carrément de nouveaux immeubles (nœuds) quand les existants sont pleins. Minikube ne construit pas d'immeuble supplémentaire.
Étape 08 · QCM

Vérifiez vos Acquis

QUESTION 01
En pratique, on crée des Deployments plutôt que des pods isolés, car un pod seul n'est pas remplacé s'il meurt.
Toujours un contrôleur

Le Deployment maintient le nombre voulu de pods en boucle. Un pod créé seul (« nu ») n'a personne pour le recréer.

QUESTION 02
Lors d'une mise à jour, le Deployment modifie en place les pods existants un par un.
Nouveau ReplicaSet

Il crée un nouveau ReplicaSet (nouvelle version) et transfère progressivement les copies de l'ancien vers le nouveau. Les pods ne sont pas modifiés, ils sont remplacés.

QUESTION 03
Le label du template de pod doit correspondre au selector du Deployment, sinon le ReplicaSet ne « voit » pas ses pods.
Le ciment des labels

Le selector et les labels du template doivent coïncider : c'est ainsi que le contrôleur identifie les pods qu'il doit gérer.

QUESTION 04
L'autoscaler (HPA) fonctionne sans rien installer de plus sur le cluster.
metrics-server requis

Le HPA décide en lisant la charge CPU/mémoire, fournie par metrics-server. Sur Minikube : minikube addons enable metrics-server.

Étape 09 · Atelier

Atelier 5 : Déployer, Scaler, Mettre à Jour

Atelier 05 · Entièrement guidé

Le cycle de vie complet d'une application web

On déploie nginx, on le met à l'échelle, on le met à jour, on casse, on répare par retour arrière. Chaque commande est fournie. Prérequis : Minikube démarré (module 3).

1 · Créer et observer
$ kubectl create namespace atelier $ kubectl config set-context --current --namespace=atelier $ kubectl create deployment web --image=nginx:1.27 --replicas=3 $ kubectl get deploy,rs,pods --show-labels
2 · Mettre à l'échelle
$ kubectl scale deployment web --replicas=5 $ kubectl get pods # 5 pods maintenant $ kubectl scale deployment web --replicas=2 $ kubectl get pods # Kubernetes en a supprime 3
3 · Mettre à jour, casser, réparer
$ kubectl set image deployment/web nginx=nginx:1.28 $ kubectl rollout status deployment/web Provoquer une panne : une image qui n'existe pas $ kubectl set image deployment/web nginx=nginx:version-bidon $ kubectl get pods # etat ImagePullBackOff : la MAJ est bloquee Reparation : retour arriere $ kubectl rollout undo deployment/web $ kubectl get pods # tout repasse en Running
Validation

Réussi si vous avez vu : le nombre de pods suivre vos ordres de scale, une mise à jour réussie passer en Running, une mauvaise image rester bloquée en ImagePullBackOff, et le rollout undo tout réparer. Pour nettoyer : kubectl delete namespace atelier.

Étape 10 · Conclusion

Récapitulatif du Module 5

  • Deployment, jamais de pod nu : le contrat qui maintient N copies en vie, en continu.
  • La hiérarchie : Deployment > ReplicaSet (un par version) > Pods (jetables).
  • Labels = le ciment : les sélecteurs relient contrôleurs, pods et bientôt services.
  • Namespaces : des ailes isolées pour organiser et cloisonner le cluster.
  • Rolling update / rollback : changer de version sans coupure, revenir en arrière en une commande.
  • HPA : ajuster le nombre de copies automatiquement (via metrics-server).
Côté résidence
Le syndic maintient nos appartements loués et sait rénover sans vider l'immeuble. Problème suivant : nos appartements changent sans cesse de locataire (et d'adresse IP). Comment les visiteurs les trouvent-ils ? Mais d'abord, un service à installer dans chaque immeuble : la supervision.
